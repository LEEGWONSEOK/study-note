# Chapter 6. 이미지 레이어와 캐시

## 6.1 레이어 구조란?

Docker 이미지는 **레이어(Layer)** 의 스택으로 구성됩니다. 각 레이어는 이전 레이어와의 **차이점(diff)** 만 저장합니다.

> **핵심**: 레이어는 **불변(immutable)** 이며 **공유** 가 가능합니다.

```
nginx 이미지 레이어 구조
┌────────────────────────────────────┐
│ Layer 4: nginx 설정 (읽기 전용)     │ ← 37B
├────────────────────────────────────┤
│ Layer 3: nginx 바이너리 설치        │ ← 58MB
├────────────────────────────────────┤
│ Layer 2: 패키지 목록 업데이트       │ ← 3.4MB
├────────────────────────────────────┤
│ Layer 1: Debian slim 베이스        │ ← 74MB
└────────────────────────────────────┘
```

## 6.2 Union File System

Docker는 **Union File System (UnionFS)** 을 사용하여 여러 레이어를 하나의 파일시스템처럼 보이게 합니다.

```
컨테이너 View (사용자에게 보이는 것)
┌────────────────────────────────────┐
│        통합 파일시스템              │
│  /etc/nginx/nginx.conf              │
│  /usr/bin/nginx                     │
│  /usr/share/nginx/html/             │
│  ...                                │
└────────────────────────────────────┘
         ▲ 병합된 뷰
┌────────┴───────────────────────────┐
│ 컨테이너 레이어 (읽기/쓰기)          │ ← 새 파일, 수정 내용
├────────────────────────────────────┤
│ Layer 4 (읽기 전용)                 │
├────────────────────────────────────┤
│ Layer 3 (읽기 전용)                 │
├────────────────────────────────────┤
│ Layer 2 (읽기 전용)                 │
├────────────────────────────────────┤
│ Layer 1 (읽기 전용)                 │
└────────────────────────────────────┘
```

### Copy-on-Write (CoW)

컨테이너에서 파일을 수정할 때:
1. 이미지 레이어(읽기 전용)에서 파일을 복사
2. 컨테이너 레이어(읽기/쓰기)에 복사본을 저장
3. 복사본을 수정

```bash
# 원본 파일은 이미지 레이어에 그대로
# 컨테이너 레이어에만 수정된 복사본 존재
docker run -it nginx bash
root@abc:/# echo "hello" >> /etc/nginx/nginx.conf
# → 이미지의 nginx.conf는 변경되지 않음
# → 컨테이너 레이어에만 수정된 복사본 생성
```

## 6.3 레이어 캐시 동작 원리

Docker는 이미지를 빌드할 때 각 명령어의 레이어를 **캐시**합니다.

```dockerfile
# Dockerfile 예시
FROM ubuntu:22.04          # Layer 1
RUN apt-get update         # Layer 2
RUN apt-get install -y java # Layer 3
COPY app.jar /app/          # Layer 4
```

**첫 번째 빌드**:
```
Step 1/4 : FROM ubuntu:22.04
 ---> 08d22c0ceb15
Step 2/4 : RUN apt-get update
 ---> Running in abc123def456
Step 3/4 : RUN apt-get install -y java
 ---> Running in ghi789jkl012
Step 4/4 : COPY app.jar /app/
 ---> Running in mno345pqr678
```

**두 번째 빌드 (app.jar 변경 후)**:
```
Step 1/4 : FROM ubuntu:22.04
 ---> 08d22c0ceb15         (캐시 사용)
Step 2/4 : RUN apt-get update
 ---> Using cache          (캐시 사용)
Step 3/4 : RUN apt-get install -y java
 ---> Using cache          (캐시 사용)
Step 4/4 : COPY app.jar /app/
 ---> Running in mno345pqr678  (캐시 무효화! 파일 변경됨)
```

> **중요**: 특정 레이어가 변경되면 이후 모든 레이어의 캐시가 무효화됩니다.

## 6.4 캐시 최적화 방법

### 나쁜 예 (캐시 비효율)

```dockerfile
FROM node:18-alpine
WORKDIR /app

# 소스 코드 전체를 먼저 복사
COPY . .                    # ← 코드 수정 시 캐시 무효화

# 의존성 설치 (매번 재실행!)
RUN npm install             # ← 느림!

CMD ["node", "server.js"]
```

**문제**: 코드를 조금만 수정해도 `npm install`이 매번 실행됩니다.

### 좋은 예 (캐시 최적화)

```dockerfile
FROM node:18-alpine
WORKDIR /app

# 의존성 파일만 먼저 복사
COPY package*.json ./       # ← package.json 변경 시에만 캐시 무효화

# 의존성 설치 (캐시 활용!)
RUN npm install             # ← package.json 안 바뀌면 캐시 사용

# 소스 코드 복사
COPY . .                    # ← 소스 코드 변경은 여기에만 영향

CMD ["node", "server.js"]
```

**결과**: 코드만 수정하면 `npm install`이 캐시에서 빠르게 완료됩니다.

### Java Spring Boot 최적화 예시

```dockerfile
FROM maven:3.9-openjdk-17 AS build
WORKDIR /app

# 의존성 파일 먼저 복사
COPY pom.xml .
RUN mvn dependency:go-offline -B   # 의존성만 먼저 다운로드

# 소스 코드 복사 후 빌드
COPY src ./src
RUN mvn clean package -DskipTests

FROM openjdk:17-jdk-slim
COPY --from=build /app/target/app.jar /app/app.jar
CMD ["java", "-jar", "/app/app.jar"]
```

### 캐시 무효화 팁

```bash
# 특정 레이어부터 캐시 사용 안 함
docker build --no-cache .

# 빌드 인수로 캐시 무효화 제어
ARG CACHEBUST=1
RUN git clone ... # CACHEBUST가 바뀌면 이 레이어부터 재실행
```

```bash
# 크기 기준으로 레이어 분석
docker history --format "{{.Size}}\t{{.CreatedBy}}" nginx | sort -rh | head -10
```

## 6.6 이미지 크기 최적화 전략

### 1. 적절한 베이스 이미지 선택

```
ubuntu:22.04   → 77.8MB
debian:slim    → 74.8MB
debian:bookworm-slim → 74.8MB
alpine:3.18    → 7.33MB    ← 권장 (패키지 충돌 없을 때)
scratch        → 0B         ← 바이너리만 있는 이미지 (Go 등)
```

### 2. RUN 명령어 최소화

```dockerfile
# 나쁜 예 - 레이어 3개 생성
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git

# 좋은 예 - 레이어 1개, 캐시 정리까지
RUN apt-get update && apt-get install -y \
    curl \
    git \
    && rm -rf /var/lib/apt/lists/*
```

### 3. 멀티스테이지 빌드 활용

```dockerfile
# 빌드 스테이지 (크고 무거운 빌드 도구 사용)
FROM maven:3.9-openjdk-17 AS build
COPY . .
RUN mvn package

# 실행 스테이지 (가벼운 JRE만 사용)
FROM openjdk:17-jre-slim
COPY --from=build target/app.jar .
```

### 4. .dockerignore 파일 활용

```
# .dockerignore
.git
.gitignore
node_modules
npm-debug.log
*.md
*.log
target/
dist/
build/
.env
.env.*
```

### 5. 이미지 크기 비교 예시

| 전략 | 이미지 크기 |
|------|-----------|
| `ubuntu + JDK + 앱` | 800MB+ |
| `openjdk:17-jdk-slim + 앱` | 400MB |
| `openjdk:17-jre-slim + 앱` | 250MB |
| 멀티스테이지 (JRE slim) | 200MB |
| 멀티스테이지 (Alpine JRE) | 100MB |
| GraalVM Native Image | 50MB 이하 |

## 6.7 Alpine Linux 활용

Alpine은 불필요한 패키지를 제거한 **초경량 Linux 배포판**입니다.

```bash
# Alpine 기반 이미지 크기
node:18         → 991MB
node:18-slim    → 246MB
node:18-alpine  → 127MB    ← 7.7배 작음!
```

### Alpine에서 패키지 설치

Alpine은 `apk` 패키지 매니저를 사용합니다:

```dockerfile
FROM alpine:3.18

# 패키지 설치
RUN apk add --no-cache \
    curl \
    bash \
    git

# 캐시 정리 (--no-cache로 이미 방지됨)
```

### Alpine 주의사항

```dockerfile
# 문제: alpine은 glibc 대신 musl libc 사용
# 일부 바이너리가 동작하지 않을 수 있음

# 해결: glibc 호환 레이어 추가
FROM alpine:3.18
RUN apk add --no-cache libc6-compat
```

## 6.8 레이어 공유의 이점

여러 이미지가 같은 베이스 이미지를 공유하면 디스크 공간이 절약됩니다:

```
이미지 A (openjdk:17 + app-a)
이미지 B (openjdk:17 + app-b)

디스크에는 openjdk:17 레이어가 한 번만 저장됨!
```

```bash
# 실제 디스크 사용량 확인
docker system df
# TYPE            SIZE      RECLAIMABLE
# Images          2.5GB     1.2GB (공유 레이어 제외)
```

## 핵심 요약

1. **레이어**: 이미지는 불변 레이어의 스택, 차이점만 저장
2. **UnionFS**: 여러 레이어를 하나의 파일시스템처럼 표시
3. **CoW**: 파일 수정 시 컨테이너 레이어에 복사본 생성
4. **캐시 최적화**: 변경 빈도가 낮은 레이어를 먼저 배치
5. **이미지 최소화**: Alpine 사용, RUN 명령어 합치기, 캐시 정리
6. **레이어 공유**: 같은 베이스 이미지 레이어는 한 번만 저장
