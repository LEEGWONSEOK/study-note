# Chapter 25. 쿼리 최적화

## 25.1 쿼리 최적화란?

### 정의

```
쿼리 최적화:
같은 결과를 더 빠르게 얻는 기술

비유: 요리 순서
┌─────────────────────────────────┐
│ ❌ 비효율적:                    │
│ 1. 모든 재료 꺼내기             │
│ 2. 다 씻기                      │
│ 3. 필요한 것만 선택             │
│                                 │
│ ✅ 효율적:                      │
│ 1. 필요한 재료만 꺼내기         │
│ 2. 필요한 것만 씻기             │
│ 3. 바로 조리                    │
└─────────────────────────────────┘

최소한의 작업으로 최대 효율!
```

### 최적화 원칙

```
1. 필요한 데이터만 읽기 (SELECT *)
2. 필요한 행만 읽기 (WHERE, LIMIT)
3. 인덱스 활용
4. JOIN 최소화
5. 서브쿼리 최적화
6. 집계 최적화
```

## 25.2 SELECT 최적화

### SELECT * 피하기

```sql
-- ❌ 나쁜 예: 모든 컬럼
SELECT * FROM users;
-- 문제:
-- - 불필요한 데이터 전송
-- - 네트워크 대역폭 낭비
-- - 메모리 낭비

-- ✅ 좋은 예: 필요한 컬럼만
SELECT id, name, email FROM users;
-- 장점:
-- - 데이터 전송량 감소
-- - Index Only Scan 가능
-- - 캐시 효율 향상
```

### 커버링 인덱스 활용

```sql
-- 자주 조회하는 컬럼
SELECT id, email, name FROM users WHERE email = 'alice@example.com';

-- 커버링 인덱스 생성
CREATE INDEX idx_users_email_id_name ON users(email, id, name);

-- 또는 INCLUDE 사용 (PostgreSQL 11+)
CREATE INDEX idx_users_email_include ON users(email) INCLUDE (id, name);

-- Index Only Scan (가장 빠름!)
EXPLAIN ANALYZE
SELECT id, email, name FROM users WHERE email = 'alice@example.com';
-- Index Only Scan using idx_users_email_include
-- Execution Time: 0.05 ms
```

## 25.3 WHERE 최적화

### 인덱스 사용 조건

```sql
-- ✅ 인덱스 사용
SELECT * FROM users WHERE age = 25;
SELECT * FROM users WHERE age > 20;
SELECT * FROM users WHERE age BETWEEN 20 AND 30;

-- ❌ 인덱스 미사용
SELECT * FROM users WHERE age + 1 = 26;  -- 함수 적용
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';  -- 함수
SELECT * FROM users WHERE age::TEXT = '25';  -- 타입 변환
```

### 함수 인덱스

```sql
-- 소문자 검색
-- ❌ 느림
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- ✅ 빠름: 함수 인덱스
CREATE INDEX idx_users_email_lower ON users(LOWER(email));

SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- Index Scan using idx_users_email_lower
```

### OR vs UNION

```sql
-- ❌ 느림: OR (인덱스 사용 어려움)
SELECT * FROM users WHERE age = 25 OR country = 'Korea';
-- Seq Scan

-- ✅ 빠름: UNION (각각 인덱스 사용)
SELECT * FROM users WHERE age = 25
UNION
SELECT * FROM users WHERE country = 'Korea';
-- Index Scan (두 번)

-- 중복 제거 필요 없으면 UNION ALL (더 빠름)
SELECT * FROM users WHERE age = 25
UNION ALL
SELECT * FROM users WHERE country = 'Korea';
```

### IN vs EXISTS

```sql
-- 서브쿼리 결과가 작을 때: IN
SELECT * FROM users
WHERE id IN (SELECT user_id FROM posts WHERE created_at > '2024-01-01');

-- 메인 테이블이 작을 때: EXISTS (일반적으로 더 빠름)
SELECT * FROM users u
WHERE EXISTS (
  SELECT 1 FROM posts p
  WHERE p.user_id = u.id AND p.created_at > '2024-01-01'
);
-- EXISTS는 첫 매칭에서 중단!
```

## 25.4 JOIN 최적화

### JOIN 순서

```sql
-- ❌ 나쁜 예: 큰 테이블 먼저
SELECT *
FROM posts p  -- 100만 건
JOIN users u ON p.user_id = u.id  -- 10만 건
WHERE u.country = 'Korea';  -- 1만 건

-- ✅ 좋은 예: 작은 테이블 먼저 (필터링)
SELECT *
FROM users u  -- 10만 건
JOIN posts p ON p.user_id = u.id  -- 필터링 후 JOIN
WHERE u.country = 'Korea';  -- 1만 건으로 줄임

-- PostgreSQL은 자동 최적화하지만 명시적으로 작성하는 것이 좋음
```

### JOIN 조건에 인덱스

```sql
-- ❌ 느림: 인덱스 없음
SELECT u.name, p.title
FROM users u
JOIN posts p ON u.id = p.user_id;
-- Hash Join (느림)

-- ✅ 빠름: 인덱스 있음
CREATE INDEX idx_posts_user_id ON posts(user_id);

SELECT u.name, p.title
FROM users u
JOIN posts p ON u.id = p.user_id;
-- Nested Loop Join (빠름)
```

### LEFT JOIN → INNER JOIN

```sql
-- ❌ 불필요한 LEFT JOIN
SELECT u.name, p.title
FROM users u
LEFT JOIN posts p ON u.id = p.user_id
WHERE p.id IS NOT NULL;  -- NULL 제외
-- LEFT JOIN 의미 없음!

-- ✅ INNER JOIN으로 변경
SELECT u.name, p.title
FROM users u
INNER JOIN posts p ON u.id = p.user_id;
-- 더 빠름!
```

### JOIN 수 최소화

```sql
-- ❌ 과도한 JOIN
SELECT u.name, p.title, c.content, l.created_at
FROM users u
JOIN posts p ON u.id = p.user_id
JOIN comments c ON p.id = c.post_id
JOIN likes l ON p.id = l.post_id;
-- 4개 테이블 JOIN (느림)

-- ✅ 필요한 것만 JOIN
SELECT u.name, p.title
FROM users u
JOIN posts p ON u.id = p.user_id;

-- 댓글 수는 서브쿼리나 별도 쿼리로
SELECT
  u.name,
  p.title,
  (SELECT COUNT(*) FROM comments WHERE post_id = p.id) AS comment_count
FROM users u
JOIN posts p ON u.id = p.user_id;
```

## 25.5 서브쿼리 최적화

### 상관 서브쿼리 → JOIN

```sql
-- ❌ 느림: 상관 서브쿼리 (N번 실행)
SELECT
  u.name,
  (SELECT COUNT(*) FROM posts WHERE user_id = u.id) AS post_count
FROM users u;
-- users 100만 건이면 서브쿼리 100만 번 실행!

-- ✅ 빠름: JOIN + GROUP BY
SELECT
  u.name,
  COUNT(p.id) AS post_count
FROM users u
LEFT JOIN posts p ON u.id = p.user_id
GROUP BY u.id, u.name;
-- 한 번에 처리!
```

### WHERE 서브쿼리 → JOIN

```sql
-- ❌ 느림: 서브쿼리
SELECT * FROM users
WHERE id IN (SELECT user_id FROM posts WHERE created_at > '2024-01-01');

-- ✅ 빠름: JOIN
SELECT DISTINCT u.*
FROM users u
INNER JOIN posts p ON u.id = p.user_id
WHERE p.created_at > '2024-01-01';
```

### WITH (CTE) 활용

```sql
-- 복잡한 서브쿼리 반복
SELECT * FROM (
  SELECT user_id, COUNT(*) AS cnt FROM posts GROUP BY user_id
) AS t1
JOIN (
  SELECT user_id, COUNT(*) AS cnt FROM posts GROUP BY user_id
) AS t2 ON t1.user_id = t2.user_id;
-- 같은 서브쿼리 두 번!

-- ✅ WITH로 한 번만 실행
WITH post_counts AS (
  SELECT user_id, COUNT(*) AS cnt FROM posts GROUP BY user_id
)
SELECT * FROM post_counts t1
JOIN post_counts t2 ON t1.user_id = t2.user_id;
```

## 25.6 집계 최적화

### DISTINCT 최소화

```sql
-- ❌ 불필요한 DISTINCT
SELECT DISTINCT user_id FROM posts;
-- 정렬 + 중복 제거 오버헤드

-- ✅ GROUP BY 사용
SELECT user_id FROM posts GROUP BY user_id;
-- 더 빠르고 추가 집계 가능

-- ✅✅ 또는 EXISTS
SELECT DISTINCT u.id FROM users u
WHERE EXISTS (SELECT 1 FROM posts p WHERE p.user_id = u.id);
```

### COUNT(*) vs COUNT(column)

```sql
-- ✅ COUNT(*): NULL 포함, 빠름
SELECT COUNT(*) FROM users;

-- ❌ COUNT(column): NULL 제외, 느림
SELECT COUNT(email) FROM users;
-- email이 NOT NULL이면 COUNT(*)와 동일하므로 COUNT(*) 사용

-- COUNT(DISTINCT)는 더 느림
SELECT COUNT(DISTINCT user_id) FROM posts;
-- 필요한 경우만 사용
```

### 윈도우 함수 활용

```sql
-- ❌ 서브쿼리로 순위
SELECT
  u.name,
  (SELECT COUNT(*) + 1 FROM users WHERE score > u.score) AS rank
FROM users u;

-- ✅ 윈도우 함수
SELECT
  name,
  RANK() OVER (ORDER BY score DESC) AS rank
FROM users;
-- 한 번의 스캔!
```

## 25.7 LIMIT과 OFFSET 최적화

### OFFSET 문제

```sql
-- ❌ 느림: OFFSET이 크면
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10 OFFSET 100000;
-- 100,010개 읽고 10개만 반환!

-- ✅ 빠름: 커서 기반 페이지네이션
SELECT * FROM posts
WHERE created_at < '2024-01-01 10:00:00'
ORDER BY created_at DESC
LIMIT 10;
-- 인덱스 사용 + 필요한 만큼만 읽기
```

### Keyset Pagination

```sql
-- 첫 페이지
SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 10;
-- 마지막 행: id=100, created_at='2024-01-15 10:00:00'

-- 다음 페이지 (OFFSET 대신)
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < ('2024-01-15 10:00:00', 100)
ORDER BY created_at DESC, id DESC
LIMIT 10;
-- 인덱스로 바로 찾기!

-- 인덱스
CREATE INDEX idx_posts_created_id ON posts(created_at DESC, id DESC);
```

## 25.8 배치 처리 최적화

### 배치 INSERT

```sql
-- ❌ 느림: 하나씩 INSERT
FOR i IN 1..10000 LOOP
  INSERT INTO users (name, email) VALUES ('User' || i, 'user' || i || '@ex.com');
END LOOP;
-- 10,000번 INSERT

-- ✅ 빠름: 배치 INSERT
INSERT INTO users (name, email)
SELECT 'User' || i, 'user' || i || '@ex.com'
FROM generate_series(1, 10000) AS i;
-- 한 번에!

-- 또는
INSERT INTO users (name, email) VALUES
('User1', 'user1@ex.com'),
('User2', 'user2@ex.com'),
...
('User10000', 'user10000@ex.com');
```

### 배치 UPDATE

```sql
-- ❌ 느림: 하나씩
UPDATE users SET status = 'active' WHERE id = 1;
UPDATE users SET status = 'active' WHERE id = 2;
...

-- ✅ 빠름: 한 번에
UPDATE users SET status = 'active' WHERE id IN (1, 2, 3, ...);

-- 또는 임시 테이블 활용
CREATE TEMP TABLE temp_updates (id INT, status VARCHAR);
INSERT INTO temp_updates VALUES (1, 'active'), (2, 'inactive'), ...;

UPDATE users u
SET status = t.status
FROM temp_updates t
WHERE u.id = t.id;
```

## 25.9 실전 최적화 패턴

### 패턴 1: N+1 쿼리 해결

```sql
-- ❌ N+1 문제
-- 1. 사용자 조회
SELECT * FROM users LIMIT 10;  -- 1번

-- 2. 각 사용자의 게시글 수 조회
SELECT COUNT(*) FROM posts WHERE user_id = 1;  -- 10번
SELECT COUNT(*) FROM posts WHERE user_id = 2;
...
-- 총 11번 쿼리!

-- ✅ 해결: JOIN
SELECT
  u.id,
  u.name,
  COUNT(p.id) AS post_count
FROM users u
LEFT JOIN posts p ON u.id = p.user_id
WHERE u.id IN (1, 2, 3, ...)
GROUP BY u.id, u.name;
-- 1번 쿼리!
```

### 패턴 2: 중복 계산 제거

```sql
-- ❌ 중복 계산
SELECT
  (SELECT COUNT(*) FROM posts WHERE user_id = u.id) AS post_count,
  (SELECT COUNT(*) FROM comments WHERE user_id = u.id) AS comment_count,
  (SELECT MAX(created_at) FROM posts WHERE user_id = u.id) AS last_post
FROM users u;
-- posts를 3번 읽음!

-- ✅ 한 번에 계산
SELECT
  u.id,
  COUNT(DISTINCT p.id) AS post_count,
  COUNT(DISTINCT c.id) AS comment_count,
  MAX(p.created_at) AS last_post
FROM users u
LEFT JOIN posts p ON u.id = p.user_id
LEFT JOIN comments c ON u.id = c.user_id
GROUP BY u.id;
```

### 패턴 3: 조건부 집계

```sql
-- ❌ 여러 쿼리
SELECT COUNT(*) FROM orders WHERE status = 'pending';
SELECT COUNT(*) FROM orders WHERE status = 'completed';
SELECT COUNT(*) FROM orders WHERE status = 'cancelled';
-- 3번 쿼리!

-- ✅ 한 번에
SELECT
  COUNT(*) FILTER (WHERE status = 'pending') AS pending_count,
  COUNT(*) FILTER (WHERE status = 'completed') AS completed_count,
  COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled_count
FROM orders;
-- 1번 쿼리!

-- 또는 CASE
SELECT
  COUNT(CASE WHEN status = 'pending' THEN 1 END) AS pending_count,
  COUNT(CASE WHEN status = 'completed' THEN 1 END) AS completed_count,
  COUNT(CASE WHEN status = 'cancelled' THEN 1 END) AS cancelled_count
FROM orders;
```

### 패턴 4: 파티션별 TOP N

```sql
-- ❌ 느림: 서브쿼리
SELECT * FROM (
  SELECT *, (
    SELECT COUNT(*) + 1
    FROM products p2
    WHERE p2.category_id = p1.category_id AND p2.price > p1.price
  ) AS rank
  FROM products p1
) t
WHERE rank <= 3;

-- ✅ 빠름: 윈도우 함수
SELECT * FROM (
  SELECT
    *,
    ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC) AS rank
  FROM products
) t
WHERE rank <= 3;
```

## 25.10 캐싱 전략

### Materialized View

```sql
-- 복잡한 집계 쿼리 (느림)
SELECT
  DATE(created_at) AS date,
  COUNT(*) AS order_count,
  SUM(total_amount) AS revenue
FROM orders
GROUP BY DATE(created_at);
-- 매번 전체 테이블 스캔!

-- Materialized View로 캐싱
CREATE MATERIALIZED VIEW daily_stats AS
SELECT
  DATE(created_at) AS date,
  COUNT(*) AS order_count,
  SUM(total_amount) AS revenue
FROM orders
GROUP BY DATE(created_at);

CREATE UNIQUE INDEX idx_daily_stats_date ON daily_stats(date);

-- 빠른 조회
SELECT * FROM daily_stats WHERE date >= CURRENT_DATE - 30;

-- 정기적 갱신 (pg_cron)
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_stats;
```

### 계산 컬럼

```sql
-- 자주 계산하는 값
SELECT *, (price * quantity) AS total FROM order_items;

-- Generated Column으로 저장 (PostgreSQL 12+)
ALTER TABLE order_items
ADD COLUMN total NUMERIC GENERATED ALWAYS AS (price * quantity) STORED;

-- 인덱스 추가
CREATE INDEX idx_order_items_total ON order_items(total);

-- 빠른 검색
SELECT * FROM order_items WHERE total > 100000;
```

## 25.11 실전 시나리오

### 시나리오 1: 대시보드 최적화

```sql
-- ❌ 느린 대시보드 (여러 쿼리)
-- 1. 오늘 주문 수
SELECT COUNT(*) FROM orders WHERE DATE(created_at) = CURRENT_DATE;

-- 2. 오늘 매출
SELECT SUM(total_amount) FROM orders WHERE DATE(created_at) = CURRENT_DATE;

-- 3. 활성 사용자 수
SELECT COUNT(DISTINCT user_id) FROM orders WHERE created_at >= NOW() - INTERVAL '7 days';

-- ✅ 최적화: 한 번에 조회
SELECT
  COUNT(*) FILTER (WHERE DATE(created_at) = CURRENT_DATE) AS today_orders,
  SUM(total_amount) FILTER (WHERE DATE(created_at) = CURRENT_DATE) AS today_revenue,
  COUNT(DISTINCT user_id) FILTER (WHERE created_at >= NOW() - INTERVAL '7 days') AS active_users
FROM orders
WHERE created_at >= CURRENT_DATE;
-- 한 번의 스캔!

-- ✅✅ Materialized View (더 빠름)
CREATE MATERIALIZED VIEW dashboard_stats AS
SELECT
  CURRENT_DATE AS stats_date,
  COUNT(*) AS today_orders,
  SUM(total_amount) AS today_revenue,
  (SELECT COUNT(DISTINCT user_id) FROM orders
   WHERE created_at >= NOW() - INTERVAL '7 days') AS active_users
FROM orders
WHERE DATE(created_at) = CURRENT_DATE;

-- 1시간마다 갱신
SELECT cron.schedule('refresh-dashboard', '0 * * * *',
  'REFRESH MATERIALIZED VIEW dashboard_stats');
```

### 시나리오 2: 검색 최적화

```sql
-- ❌ 느린 검색
SELECT * FROM products
WHERE name LIKE '%laptop%'
   OR description LIKE '%laptop%'
   OR brand LIKE '%laptop%';
-- Seq Scan (인덱스 못 씀)

-- ✅ Full Text Search
ALTER TABLE products ADD COLUMN search_vector tsvector;

UPDATE products
SET search_vector =
  setweight(to_tsvector('english', name), 'A') ||
  setweight(to_tsvector('english', COALESCE(description, '')), 'B') ||
  setweight(to_tsvector('english', COALESCE(brand, '')), 'C');

CREATE INDEX idx_products_search ON products USING GIN(search_vector);

-- 빠른 검색
SELECT * FROM products
WHERE search_vector @@ to_tsquery('english', 'laptop')
ORDER BY ts_rank(search_vector, to_tsquery('english', 'laptop')) DESC;
```

## 핵심 요약

### 쿼리 최적화 체크리스트

```
✅ SELECT
□ SELECT * 피하기
□ 필요한 컬럼만
□ 커버링 인덱스 활용

✅ WHERE
□ 인덱스 활용 가능하게
□ 함수 적용 피하기
□ OR → UNION
□ IN → EXISTS

✅ JOIN
□ 작은 테이블 먼저
□ JOIN 조건에 인덱스
□ LEFT JOIN → INNER JOIN
□ JOIN 수 최소화

✅ 서브쿼리
□ 상관 서브쿼리 → JOIN
□ WHERE 서브쿼리 → JOIN
□ WITH (CTE) 활용

✅ 집계
□ DISTINCT 최소화
□ COUNT(*) 사용
□ 윈도우 함수 활용

✅ 페이지네이션
□ OFFSET 피하기
□ Keyset Pagination

✅ 배치
□ 배치 INSERT/UPDATE
□ 임시 테이블 활용
```

### 최적화 순서

```
1. EXPLAIN ANALYZE로 병목 찾기
2. 인덱스 추가/최적화
3. 쿼리 재작성
4. 통계 업데이트 (ANALYZE)
5. 캐싱 (Materialized View)
6. 성능 재측정
```
