## 1. 백업이란? (비유로 이해하기)

### 📚 집을 짓는 과정에 비유하면

```
백업 = 집의 설계도 + 사진 + 재료 보관
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🏠 논리적 백업 (Logical Backup)
   ├─ 설계도를 복사
   ├─ "어떻게 지었는지" 기록
   └─ 나중에 똑같이 다시 지을 수 있음

🧱 물리적 백업 (Physical Backup)
   ├─ 집 전체를 사진 촬영
   ├─ "현재 상태" 그대로 보존
   └─ 빠르게 복원 가능

📸 스냅샷 (Snapshot)
   ├─ 특정 시점의 사진
   ├─ 순간 포착
   └─ 빠른 백업/복원
```

## 2. 왜 백업이 필요한가?

### 실제 발생 가능한 재해 시나리오

#### 🔥 시나리오 1: 하드웨어 장애
```bash
# 갑자기 디스크가 고장남
$ psql -U postgres
psql: error: could not connect to server:
  could not open file "/var/lib/postgresql/data/base/...":
  Input/output error

# 백업이 없으면?
❌ 모든 데이터 손실
❌ 비즈니스 중단
❌ 고객 신뢰 상실
```

#### 💥 시나리오 2: 실수로 데이터 삭제
```sql
-- 😱 실수: WHERE 절 없이 DELETE
DELETE FROM users;
-- Query returned successfully: 1,000,000 rows affected in 234 ms.

-- 백업이 있으면?
✅ 1시간 전 백업으로 복원
✅ 손실 최소화
✅ 빠른 복구
```

#### 🦠 시나리오 3: 랜섬웨어 공격
```bash
# 데이터베이스가 암호화됨
Your database has been encrypted.
Pay 10 BTC to recover.

# 백업이 있고, 격리되어 있으면?
✅ 암호화된 DB 무시
✅ 깨끗한 백업으로 복원
✅ 몸값 지불 불필요
```

## 3. 백업 유형 비교

### 📊 논리적 백업 (Logical Backup)

#### 특징
```
논리적 백업 = SQL 문으로 저장
━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 장점:
   ├─ 사람이 읽을 수 있음 (SQL)
   ├─ 선택적 백업 가능 (특정 테이블만)
   ├─ 버전 간 호환성 좋음
   └─ 압축률 높음

❌ 단점:
   ├─ 백업/복원 속도 느림
   ├─ 대용량 DB에 비효율적
   └─ CPU 리소스 많이 사용
```

#### 실제 논리적 백업 예시
```sql
-- pg_dump로 생성된 백업 파일 내용
--
-- PostgreSQL database dump
--

SET statement_timeout = 0;
SET client_encoding = 'UTF8';

CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100) UNIQUE
);

INSERT INTO users (id, name, email) VALUES
(1, 'Alice', 'alice@example.com'),
(2, 'Bob', 'bob@example.com');
```

### 🧱 물리적 백업 (Physical Backup)

#### 특징
```
물리적 백업 = 데이터 파일 복사
━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 장점:
   ├─ 백업/복원 속도 매우 빠름
   ├─ 대용량 DB에 효율적
   ├─ 전체 클러스터 백업
   └─ PITR (Point-In-Time Recovery) 가능

❌ 단점:
   ├─ 사람이 읽을 수 없음 (바이너리)
   ├─ 같은 버전/아키텍처에서만 복원
   ├─ 전체 백업만 가능 (선택 불가)
   └─ 압축률 낮음
```

#### 물리적 백업 디렉토리 구조
```bash
# PostgreSQL 데이터 디렉토리
/var/lib/postgresql/14/main/
├── base/               # 데이터베이스 파일
│   ├── 1/
│   ├── 13757/
│   └── 16384/
├── global/             # 클러스터 전역 데이터
├── pg_wal/             # WAL (Write-Ahead Log)
├── pg_xact/            # 트랜잭션 커밋 상태
└── postgresql.conf     # 설정 파일

# 이 전체를 복사 = 물리적 백업
```

## 4. 백업 전략: 3-2-1 규칙

### 🎯 업계 표준 백업 전략

```
3-2-1 백업 규칙
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

3️⃣  3개의 복사본
    ├─ 원본 1개
    └─ 백업 2개

2️⃣  2개의 서로 다른 매체
    ├─ 로컬 디스크
    └─ 클라우드 스토리지

1️⃣  1개는 오프사이트 (원격지)
    └─ 재해로부터 보호
```

#### 실전 적용 예시
```yaml
# 우리 회사의 백업 전략
백업 복사본:
  원본: 프로덕션 DB 서버
  백업1: 같은 IDC의 백업 서버 (물리적 백업)
  백업2: AWS S3 (논리적 백업)

저장 매체:
  로컬: SSD RAID 10
  원격: AWS S3 Glacier

오프사이트:
  AWS 서울 리전 + 도쿄 리전 (교차 복제)
```

## 5. RPO와 RTO

### 📐 목표 복구 지표

```
RPO (Recovery Point Objective)
복구 시점 목표 = 얼마나 많은 데이터 손실을 감수할 것인가?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

10:00 ─────────┐
10:30          │  ← 백업 주기
11:00 ─────────┤
11:30          │
12:00 💥 장애  │
       ↓
       복원 시 11:00 백업 사용
       11:00 ~ 12:00 데이터는 손실 ❌

RPO = 1시간 (최대 1시간치 데이터 손실 허용)


RTO (Recovery Time Objective)
복구 시간 목표 = 얼마나 빨리 복구할 것인가?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

12:00 💥 장애 발생
12:05    알람 수신
12:10    복구 시작
12:30    ✅ 서비스 재개

RTO = 30분 (30분 내 서비스 복구)
```

### RPO/RTO에 따른 백업 전략

| 비즈니스 | RPO | RTO | 백업 전략 |
|---------|-----|-----|----------|
| 🎮 개인 블로그 | 24시간 | 4시간 | 매일 1회 논리적 백업 |
| 📦 전자상거래 | 1시간 | 30분 | 1시간마다 물리적 백업 + WAL 아카이빙 |
| 🏦 금융 서비스 | 0초 | 즉시 | Streaming Replication + 자동 Failover |

#### 예시: 전자상거래 백업 스크립트
```bash
#!/bin/bash
# backup-ecommerce.sh
# RPO: 1시간, RTO: 30분을 위한 백업 스크립트

BACKUP_DIR="/backups/$(date +%Y%m%d)"
mkdir -p "$BACKUP_DIR"

# 1. 매 시간 물리적 백업 (pg_basebackup)
pg_basebackup -h localhost -U postgres \
  -D "$BACKUP_DIR/base_$(date +%H%M)" \
  -Fp -Xs -P

# 2. WAL 아카이빙 (연속 복구 지점)
# postgresql.conf:
#   archive_mode = on
#   archive_command = 'cp %p /backups/wal_archive/%f'

# 3. 클라우드 업로드 (오프사이트)
aws s3 sync "$BACKUP_DIR" \
  "s3://mycompany-backups/postgres/$(date +%Y%m%d)/" \
  --storage-class STANDARD_IA

# 4. 7일 이상 로컬 백업 삭제
find /backups -type d -mtime +7 -exec rm -rf {} \;

echo "✅ Backup completed at $(date)"
```

## 6. 백업 유형별 전략

### 🔄 풀 백업 (Full Backup)

```
풀 백업 = 전체 데이터베이스 백업
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[모든 데이터] ──복사──> [백업 파일]

장점: 복원 간단 (1단계)
단점: 시간/용량 많이 소요
```

#### 실습: 풀 백업
```bash
# 1. 논리적 풀 백업 (pg_dump)
pg_dump -U postgres -Fc mydb > /backups/mydb_full_$(date +%Y%m%d).dump

# 파일 크기 확인
ls -lh /backups/mydb_full_*.dump
# -rw-r--r-- 1 postgres postgres 2.3G Jan 15 03:00 mydb_full_20240115.dump

# 2. 물리적 풀 백업 (pg_basebackup)
pg_basebackup -h localhost -U postgres \
  -D /backups/base_full_$(date +%Y%m%d) \
  -Fp -Xs -P

# 디렉토리 크기 확인
du -sh /backups/base_full_*
# 5.1G    /backups/base_full_20240115
```

### 📈 증분 백업 (Incremental Backup)

```
증분 백업 = 변경된 부분만 백업
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

일요일: [풀 백업] ──────────> 10GB
월요일: [변경분만] ─────────> +500MB
화요일: [변경분만] ─────────> +300MB
수요일: [변경분만] ─────────> +400MB

복원 시: 일요일 풀 + 월~수 증분 = 완전 복원

장점: 백업 속도 빠름, 용량 적음
단점: 복원 복잡 (여러 파일 필요)
```

#### 실습: WAL 기반 증분 백업
```sql
-- 1. WAL 아카이빙 활성화 (postgresql.conf)
-- 이 설정으로 변경 로그를 별도 저장
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backups/wal_archive/%f && cp %p /backups/wal_archive/%f'
```

```bash
# 2. 베이스 백업 (일요일)
pg_basebackup -h localhost -U postgres \
  -D /backups/base_sunday \
  -Fp -Xs -P

# 3. WAL 파일들이 자동으로 아카이빙됨 (월~일)
ls /backups/wal_archive/
# 000000010000000000000001
# 000000010000000000000002
# 000000010000000000000003
# ... (변경분만 쌓임)

# 4. 복원 시: 베이스 + WAL 재생
# recovery.conf (또는 postgresql.conf):
restore_command = 'cp /backups/wal_archive/%f %p'
recovery_target_time = '2024-01-17 14:30:00'
```

### 🔀 차등 백업 (Differential Backup)

```
차등 백업 = 마지막 풀 백업 이후 모든 변경분
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

일요일: [풀 백업] ──────────> 10GB
월요일: [일요일 이후] ──────> +500MB
화요일: [일요일 이후] ──────> +800MB (월+화)
수요일: [일요일 이후] ──────> +1.2GB (월+화+수)

복원 시: 일요일 풀 + 수요일 차등 = 완전 복원

장점: 증분보다 복원 빠름
단점: 증분보다 용량 많음
```

## 7. 백업 주기 전략

### 📅 권장 백업 스케줄

#### 소규모 서비스 (< 100GB)
```bash
# 매일 자정 풀 백업
0 0 * * * /usr/local/bin/backup-full.sh

# 매 6시간마다 논리적 백업
0 */6 * * * pg_dump -U postgres mydb > /backups/mydb_$(date +\%H).dump

# 매주 일요일 장기 보관용
0 2 * * 0 /usr/local/bin/backup-weekly.sh
```

#### 중규모 서비스 (100GB ~ 1TB)
```bash
# 매주 일요일 풀 백업
0 2 * * 0 /usr/local/bin/backup-full.sh

# 매일 자정 증분 백업 (WAL)
0 0 * * 1-6 /usr/local/bin/backup-incremental.sh

# 매 시간 WAL 아카이빙 (자동)
# archive_command로 처리
```

#### 대규모 서비스 (> 1TB)
```bash
# 매주 일요일 풀 백업
0 3 * * 0 /usr/local/bin/backup-full.sh

# 연속 WAL 아카이빙 (실시간)
# archive_command + archive_timeout = 60

# Streaming Replication (Stand-by 서버)
# 실시간 복제로 RPO ≈ 0

# 매일 Stand-by에서 스냅샷
0 4 * * * ssh standby-server 'pg_basebackup ...'
```

## 8. 백업 검증

### ✅ 백업은 복원할 수 있어야 의미가 있다!

```
백업 검증의 중요성
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❌ 잘못된 가정:
   "백업 파일이 있으니 안전해!"

✅ 올바른 접근:
   "이 백업으로 실제 복원되는지 정기적으로 테스트"

📊 통계:
   - 백업 실패율: 약 34%
   - 복원 테스트 안 하는 조직: 약 60%
   - 필요 시 복원 실패: 약 25%
```

#### 백업 검증 스크립트
```bash
#!/bin/bash
# verify-backup.sh
# 백업 파일이 실제로 복원 가능한지 검증

BACKUP_FILE="/backups/mydb_full_$(date +%Y%m%d).dump"
TEST_DB="test_restore_$(date +%s)"

echo "🔍 백업 파일 검증 시작..."

# 1. 파일 존재 및 크기 확인
if [ ! -f "$BACKUP_FILE" ]; then
    echo "❌ 백업 파일 없음: $BACKUP_FILE"
    exit 1
fi

SIZE=$(stat -f%z "$BACKUP_FILE" 2>/dev/null || stat -c%s "$BACKUP_FILE" 2>/dev/null)
if [ "$SIZE" -lt 1000 ]; then
    echo "❌ 백업 파일 크기가 너무 작음: $SIZE bytes"
    exit 1
fi
echo "✅ 백업 파일 크기: $(numfmt --to=iec-i --suffix=B $SIZE)"

# 2. 테스트 DB 생성
createdb -U postgres "$TEST_DB"
echo "✅ 테스트 DB 생성: $TEST_DB"

# 3. 백업 복원 시도
pg_restore -U postgres -d "$TEST_DB" "$BACKUP_FILE" 2>&1 | tee /tmp/restore.log
if [ ${PIPESTATUS[0]} -ne 0 ]; then
    echo "❌ 복원 실패! 로그 확인: /tmp/restore.log"
    dropdb -U postgres "$TEST_DB"
    exit 1
fi
echo "✅ 복원 성공"

# 4. 데이터 무결성 검사
TABLES=$(psql -U postgres -d "$TEST_DB" -t -c "
    SELECT COUNT(*) FROM information_schema.tables
    WHERE table_schema = 'public'
")
echo "✅ 복원된 테이블 수: $TABLES"

ROWS=$(psql -U postgres -d "$TEST_DB" -t -c "
    SELECT SUM(n_live_tup) FROM pg_stat_user_tables
")
echo "✅ 총 행 수: $ROWS"

# 5. 정리
dropdb -U postgres "$TEST_DB"
echo "✅ 테스트 DB 삭제"

echo "🎉 백업 검증 완료! 백업 파일이 정상입니다."

# 6. 결과를 모니터링 시스템에 전송
curl -X POST https://monitoring.example.com/api/backup-verified \
  -H "Content-Type: application/json" \
  -d "{\"backup\":\"$BACKUP_FILE\", \"status\":\"success\", \"tables\":$TABLES, \"rows\":$ROWS}"
```

#### 정기 검증 스케줄
```bash
# 매주 월요일 오전 3시에 백업 검증
0 3 * * 1 /usr/local/bin/verify-backup.sh >> /var/log/backup-verify.log 2>&1
```

## 9. 클라우드 백업 전략

### ☁️ AWS를 활용한 백업

#### S3 백업 스크립트
```bash
#!/bin/bash
# backup-to-s3.sh

BACKUP_FILE="/backups/mydb_$(date +%Y%m%d_%H%M%S).dump"
S3_BUCKET="s3://mycompany-db-backups"

# 1. 논리적 백업 생성
pg_dump -U postgres -Fc mydb > "$BACKUP_FILE"

# 2. 백업 파일 암호화 (선택사항)
openssl enc -aes-256-cbc -salt -in "$BACKUP_FILE" \
  -out "$BACKUP_FILE.enc" -pass pass:$BACKUP_ENCRYPTION_KEY

# 3. S3 업로드 (수명주기 정책 적용)
aws s3 cp "$BACKUP_FILE.enc" \
  "$S3_BUCKET/daily/$(basename $BACKUP_FILE.enc)" \
  --storage-class STANDARD_IA \
  --metadata "source=prod-db-01,date=$(date -Iseconds)"

# 4. 로컬 백업 삭제 (S3에만 보관)
rm -f "$BACKUP_FILE" "$BACKUP_FILE.enc"

echo "✅ S3 백업 완료: $S3_BUCKET/daily/$(basename $BACKUP_FILE.enc)"
```

### 🏢 시나리오 2: 중견 기업 (안정성 중시)

```yaml
회사: 전자상거래 플랫폼
DB 크기: 500GB
예산: 월 $500
RPO: 1시간
RTO: 30분

백업 전략:
  방법:
    - 물리적 백업 (pg_basebackup) 주 1회
    - WAL 아카이빙 (연속)
    - Streaming Replication (Standby 서버)
  저장:
    - Stand-by 서버: 실시간
    - NAS: 물리 백업 7일치
    - S3: WAL 30일치
  비용:
    - Stand-by EC2: $200/월
    - S3: 500GB × $0.023 = $11.50/월
    - 전송: $50/월
    - 총: ~$262/월 ✅
```

```bash
#!/bin/bash
# enterprise-backup.sh

# 1. 매주 일요일 풀 백업
if [ "$(date +\%u)" -eq 7 ]; then
    pg_basebackup -h primary-db -U replication \
      -D /backups/base_$(date +\%Y\%m\%d) \
      -Fp -Xs -P

    # S3 업로드
    tar czf - /backups/base_$(date +\%Y\%m\%d) | \
      aws s3 cp - "s3://company-backups/postgres/base_$(date +\%Y\%m\%d).tar.gz"
fi

# 2. WAL 아카이빙 (postgresql.conf)
# archive_command = 'aws s3 cp %p s3://company-backups/wal/%f'

# 3. Stand-by 서버 상태 확인
STANDBY_LAG=$(psql -h standby-db -U postgres -t -c "
    SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))
")

if (( $(echo "$STANDBY_LAG > 300" | bc -l) )); then
    # 5분 이상 지연 시 알람
    curl -X POST $PAGERDUTY_URL \
      -d "{\"event\":\"standby_lag\", \"lag_seconds\":$STANDBY_LAG}"
fi

# 4. 14일 이상 백업 삭제
find /backups -type d -name "base_*" -mtime +14 -exec rm -rf {} \;
```

### 🏦 시나리오 3: 금융 서비스 (제로 다운타임)

```yaml
회사: 핀테크 금융 서비스
DB 크기: 2TB
규정: 금융위 7년 보관 의무
RPO: 0초
RTO: 즉시 (자동 Failover)

백업 전략:
  방법:
    - Synchronous Streaming Replication
    - 물리적 백업 매일
    - WAL 아카이빙 (무제한)
    - 별도 DR 센터
  저장:
    - Primary + Standby (동기 복제)
    - DR 센터: 비동기 복제
    - S3: 7년치 (Deep Archive)
  비용:
    - Primary + Standby: $2,000/월
    - DR 센터: $1,500/월
    - S3 (7년): $500/월
    - 총: ~$4,000/월
```

```sql
-- primary 서버 설정 (postgresql.conf)
synchronous_commit = on
synchronous_standby_names = 'standby1'
wal_level = replica
archive_mode = on
archive_command = 'aws s3 cp %p s3://fintech-wal/%f --storage-class DEEP_ARCHIVE'
archive_timeout = 60  -- 1분마다 강제 아카이빙
```

```bash
#!/bin/bash
# fintech-backup.sh

# 1. 매일 Stand-by에서 백업 (Primary 무영향)
ssh standby1 "
  pg_basebackup -h localhost -U replication \
    -D /backups/base_$(date +\%Y\%m\%d) \
    -Fp -Xs -P
"

# 2. 백업 암호화 (규정 준수)
ssh standby1 "
  tar czf - /backups/base_$(date +\%Y\%m\%d) | \
  gpg --encrypt --recipient backup@company.com | \
  aws s3 cp - s3://fintech-backups/encrypted/base_$(date +\%Y\%m\%d).tar.gz.gpg \
    --storage-class GLACIER
"

# 3. DR 센터 동기화 확인
DR_LAG=$(psql -h dr-center -U postgres -t -c "
    SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))
")

if (( $(echo "$DR_LAG > 60" | bc -l) )); then
    # 1분 이상 지연 시 긴급 알람
    curl -X POST $CRITICAL_ALERT_URL \
      -d "{\"severity\":\"critical\", \"message\":\"DR 센터 복제 지연: ${DR_LAG}초\"}"
fi

# 4. 감사 로그 기록
echo "$(date -Iseconds) | BACKUP_COMPLETED | base_$(date +\%Y\%m\%d)" >> /var/log/audit.log
```

## 📖 정리

이번 챕터에서 배운 내용:

| 개념 | 핵심 내용 |
|------|----------|
| **백업 유형** | 논리적 (SQL 문) vs 물리적 (파일 복사) |
| **3-2-1 규칙** | 3개 복사본, 2개 매체, 1개 오프사이트 |
| **RPO** | 복구 시점 목표 (데이터 손실 허용 범위) |
| **RTO** | 복구 시간 목표 (서비스 중단 허용 시간) |
| **백업 방식** | 풀 백업, 증분 백업, 차등 백업 |
| **백업 검증** | 정기적 복원 테스트 필수 |
| **클라우드 백업** | S3 수명주기로 비용 최적화 |

### 핵심 명령어
```bash
# 논리적 백업
pg_dump -U postgres -Fc mydb > backup.dump

# 물리적 백업
pg_basebackup -D /backups/base -Fp -Xs -P

# WAL 아카이빙
archive_mode = on
archive_command = 'cp %p /backups/wal/%f'

# S3 업로드
aws s3 cp backup.dump s3://bucket/path/
```

**기억하세요**: "백업이 없으면 데이터도 없습니다. 하지만 테스트하지 않은 백업도 없는 것과 같습니다!"
