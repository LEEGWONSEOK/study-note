# Chapter 15. 인덱스 최적화

## 15.1 인덱스 최적화란?

### 정의

```
인덱스 최적화:
최소한의 인덱스로 최대의 성능을 내는 기술

비유: 책장 정리
┌─────────────────────────────────┐
│ ❌ 나쁜 책장:                   │
│ - 같은 책이 여러 권 (중복)      │
│ - 안 읽는 책이 많음 (미사용)    │
│ - 찾기 어려운 분류 (비효율)     │
│                                 │
│ ✅ 좋은 책장:                   │
│ - 자주 읽는 책만 (필요한 것만)  │
│ - 주제별로 정리 (복합 인덱스)   │
│ - 빠르게 찾기 (효율적)          │
└─────────────────────────────────┘
```

### 최적화 목표

```
1. 쿼리 성능 향상
   - SELECT 속도 향상
   - JOIN 속도 향상

2. 저장 공간 절약
   - 불필요한 인덱스 제거
   - 중복 인덱스 제거

3. 쓰기 성능 유지
   - INSERT/UPDATE/DELETE 속도 유지
   - 인덱스 개수 최소화

균형점 찾기!
```

## 15.2 인덱스 선택도 (Selectivity)

### 정의

```
선택도 (Selectivity):
특정 값으로 필터링했을 때 남는 행의 비율

선택도 = DISTINCT 값 개수 / 전체 행 개수

예:
전체 사용자: 100만 명

1. 이메일 (고유값):
   - DISTINCT: 100만
   - 선택도: 100만 / 100만 = 100%
   - ✅ 인덱스 효과 좋음!

2. 성별 (M/F):
   - DISTINCT: 2
   - 선택도: 2 / 100만 = 0.0002%
   - ❌ 인덱스 효과 없음!
```

### 선택도 계산

```sql
-- 선택도 확인
SELECT
  COUNT(DISTINCT email)::FLOAT / COUNT(*) AS email_selectivity,
  COUNT(DISTINCT country)::FLOAT / COUNT(*) AS country_selectivity,
  COUNT(DISTINCT is_active)::FLOAT / COUNT(*) AS is_active_selectivity
FROM users;

--  email_selectivity | country_selectivity | is_active_selectivity
-- -------------------+---------------------+-----------------------
--  1.0               | 0.05                | 0.0000002
--  ↑ 인덱스 좋음      ↑ 보통                ↑ 인덱스 나쁨
```

### 인덱스 효과

```sql
-- ✅ 선택도 높음 (이메일)
CREATE INDEX idx_users_email ON users(email);

SELECT * FROM users WHERE email = 'alice@example.com';
-- 100만 건 → 1건 (0.0001%)
-- 인덱스 효과 극대!

-- ❌ 선택도 낮음 (성별)
CREATE INDEX idx_users_gender ON users(gender);

SELECT * FROM users WHERE gender = 'M';
-- 100만 건 → 50만 건 (50%)
-- 인덱스보다 Seq Scan이 더 빠를 수 있음!

-- PostgreSQL이 자동으로 판단
EXPLAIN SELECT * FROM users WHERE gender = 'M';
-- Seq Scan on users  ← 인덱스 있어도 사용 안 함!
```

### 부분 인덱스로 개선

```sql
-- 선택도 낮은 컬럼은 부분 인덱스
CREATE INDEX idx_premium_users ON users(is_premium)
WHERE is_premium = true;
-- 프리미엄 사용자(5%)만 인덱싱

SELECT * FROM users WHERE is_premium = true;
-- 인덱스 사용! (전체의 5%만)
```

## 15.3 커버링 인덱스 (Covering Index)

### 정의

```
커버링 인덱스 (Covering Index):
쿼리에 필요한 모든 컬럼을 인덱스에 포함

장점:
- 테이블 접근 없이 인덱스만으로 결과 반환
- Index Only Scan 사용
- 매우 빠름!
```

### 예제

```sql
-- 쿼리
SELECT email, name FROM users WHERE email = 'alice@example.com';

-- ❌ 일반 인덱스
CREATE INDEX idx_users_email ON users(email);

EXPLAIN ANALYZE
SELECT email, name FROM users WHERE email = 'alice@example.com';

-- Index Scan using idx_users_email
-- → 인덱스로 찾고, 테이블에서 name 읽음


-- ✅ 커버링 인덱스
CREATE INDEX idx_users_email_name ON users(email, name);

EXPLAIN ANALYZE
SELECT email, name FROM users WHERE email = 'alice@example.com';

-- Index Only Scan using idx_users_email_name
-- → 인덱스만으로 모든 데이터 반환! (테이블 접근 X)
-- 2배 이상 빠름!
```

### INCLUDE (PostgreSQL 11+)

```sql
-- 일반 복합 인덱스
CREATE INDEX idx_users_email_name ON users(email, name);
-- email과 name 모두 정렬됨

-- INCLUDE 사용
CREATE INDEX idx_users_email_include_name ON users(email) INCLUDE (name);
-- email만 정렬, name은 저장만 (정렬 X)
-- 인덱스 크기 작음, Index Only Scan 가능

-- 쿼리
SELECT email, name FROM users WHERE email = 'alice@example.com';
-- Index Only Scan (커버링 인덱스 효과)

SELECT email, name FROM users WHERE name = 'Alice';
-- name으로 검색 불가 (INCLUDE는 검색 불가, 저장만)
```

### 실전 예제

```sql
-- 주문 목록 조회
SELECT id, user_id, total_amount, created_at
FROM orders
WHERE user_id = 1000
ORDER BY created_at DESC
LIMIT 10;

-- ❌ 일반 인덱스
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);
-- id, total_amount는 테이블에서 읽어야 함

-- ✅ 커버링 인덱스
CREATE INDEX idx_orders_user_created_covering
ON orders(user_id, created_at DESC)
INCLUDE (id, total_amount);
-- 모든 컬럼이 인덱스에 있음 → Index Only Scan!
```

## 15.4 인덱스 스캔 방식

### Seq Scan (순차 스캔)

```sql
-- 테이블 전체 읽기
EXPLAIN SELECT * FROM users;

-- Seq Scan on users (cost=0.00..25833.00 rows=1000000 width=45)
-- → 모든 행을 순차적으로 읽음

-- 언제 사용?
-- - 인덱스 없음
-- - WHERE 조건이 대부분의 행 반환
-- - 작은 테이블
```

### Index Scan (인덱스 스캔)

```sql
-- 인덱스 사용
EXPLAIN SELECT * FROM users WHERE id = 100;

-- Index Scan using users_pkey on users (cost=0.42..8.44 rows=1 width=45)
--   Index Cond: (id = 100)
-- → 인덱스로 위치 찾고, 테이블에서 행 읽기

-- 언제 사용?
-- - 소수의 행 반환 (< 5%)
-- - PRIMARY KEY, UNIQUE 검색
```

### Index Only Scan (인덱스만 스캔)

```sql
-- 커버링 인덱스
CREATE INDEX idx_users_email_name ON users(email) INCLUDE (name);

EXPLAIN SELECT email, name FROM users WHERE email = 'alice@example.com';

-- Index Only Scan using idx_users_email_name (cost=0.42..4.44 rows=1 width=...)
--   Index Cond: (email = 'alice@example.com')
-- → 테이블 접근 없이 인덱스만 사용 (가장 빠름!)

-- 언제 사용?
-- - 커버링 인덱스
-- - 쿼리의 모든 컬럼이 인덱스에 포함
```

### Bitmap Index Scan (비트맵 스캔)

```sql
-- 여러 조건 조합
EXPLAIN SELECT * FROM users WHERE age > 20 AND country = 'Korea';

-- Bitmap Heap Scan on users (cost=12.45..1250.50 rows=500 width=45)
--   Recheck Cond: ((age > 20) AND (country = 'Korea'))
--   -> Bitmap Index Scan on idx_users_age
--   -> Bitmap Index Scan on idx_users_country

-- 언제 사용?
-- - 여러 인덱스 조합
-- - 중간 정도 행 반환 (5-50%)
-- - OR 조건
```

### 스캔 방식 비교

```
데이터 반환 비율:

0.01%  → Index Scan (매우 빠름)
  ↓
  1%   → Index Scan (빠름)
  ↓
 10%   → Bitmap Index Scan (보통)
  ↓
 50%   → Seq Scan (느림)
  ↓
100%   → Seq Scan (인덱스 의미 없음)
```

## 15.5 복합 인덱스 최적화

### 컬럼 순서 규칙

```sql
-- 테이블
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INT NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 쿼리 패턴
SELECT * FROM orders
WHERE user_id = 1000
  AND status = 'completed'
ORDER BY created_at DESC;

-- ❌ 나쁜 순서
CREATE INDEX idx_bad ON orders(created_at, status, user_id);
-- created_at이 첫 번째 → WHERE절에서 사용 안 됨!

-- ✅ 좋은 순서
CREATE INDEX idx_good ON orders(user_id, status, created_at DESC);
-- 1. user_id로 필터 (선택도 높음)
-- 2. status로 필터
-- 3. created_at로 정렬
-- → 한 번의 인덱스 스캔!
```

### 복합 인덱스 순서 원칙

```
1. 등호(=) 조건 → 먼저
2. 범위(>, <, BETWEEN) 조건 → 나중
3. 정렬(ORDER BY) → 마지막

예:
WHERE a = ? AND b > ? ORDER BY c
→ INDEX(a, b, c)

WHERE a = ? AND b = ? ORDER BY c
→ INDEX(a, b, c)

WHERE a > ? AND b = ?
→ INDEX(b, a)  ← b가 먼저!
```

### 예제

```sql
-- 쿼리 1
SELECT * FROM posts
WHERE status = 'published'
  AND created_at >= '2024-01-01'
ORDER BY created_at DESC;

-- 인덱스
CREATE INDEX idx_posts_status_created
ON posts(status, created_at DESC);
-- status(=) → created_at(범위 + 정렬)


-- 쿼리 2
SELECT * FROM orders
WHERE user_id = 1000
  AND total_amount > 10000
  AND status = 'completed';

-- 인덱스
CREATE INDEX idx_orders_user_status_amount
ON orders(user_id, status, total_amount);
-- user_id(=), status(=) → total_amount(>)
```

### 다중 쿼리 지원

```sql
-- 쿼리 패턴 3개
-- 1. WHERE user_id = ?
-- 2. WHERE user_id = ? AND status = ?
-- 3. WHERE user_id = ? AND status = ? ORDER BY created_at

-- 하나의 복합 인덱스로 모두 커버
CREATE INDEX idx_orders_user_status_created
ON orders(user_id, status, created_at DESC);

-- 쿼리 1: user_id만 사용 (앞부분만)
SELECT * FROM orders WHERE user_id = 1000;
-- Index Scan using idx_orders_user_status_created ✅

-- 쿼리 2: user_id, status 사용
SELECT * FROM orders WHERE user_id = 1000 AND status = 'completed';
-- Index Scan using idx_orders_user_status_created ✅

-- 쿼리 3: 모두 사용
SELECT * FROM orders
WHERE user_id = 1000 AND status = 'completed'
ORDER BY created_at DESC;
-- Index Scan using idx_orders_user_status_created ✅
```

## 15.6 인덱스 힌트와 통계

### 통계 업데이트

```sql
-- PostgreSQL은 통계를 사용해 쿼리 플랜 결정
-- 통계가 오래되면 잘못된 플랜 선택 가능!

-- 통계 업데이트
ANALYZE users;

-- 특정 컬럼만
ANALYZE users(email);

-- 자동 VACUUM이 주기적으로 ANALYZE 실행
-- 하지만 대량 데이터 변경 후에는 수동 실행 권장
```

### 통계 확인

```sql
-- 테이블 통계
SELECT
  schemaname,
  tablename,
  n_live_tup AS live_rows,
  n_dead_tup AS dead_rows,
  last_autovacuum,
  last_autoanalyze
FROM pg_stat_user_tables
WHERE tablename = 'users';

--  tablename | live_rows | dead_rows | last_autovacuum      | last_autoanalyze
-- -----------+-----------+-----------+----------------------+------------------
--  users     | 1000000   | 50000     | 2024-01-15 10:00:00  | 2024-01-15 10:00:00

-- dead_rows가 많으면 VACUUM 필요
VACUUM ANALYZE users;
```

### 인덱스 통계 상세

```sql
-- 컬럼별 통계
SELECT
  tablename,
  attname,
  n_distinct,
  correlation
FROM pg_stats
WHERE tablename = 'users'
  AND schemaname = 'public';

--  tablename | attname  | n_distinct | correlation
-- -----------+----------+------------+-------------
--  users     | id       | -1         | 1
--  users     | email    | -1         | 0.5
--  users     | country  | 50         | 0.1
--  users     | is_active| 2          | -0.2

-- n_distinct: DISTINCT 값 개수 (-1 = 모두 고유)
-- correlation: 물리적 정렬 상관관계 (1 = 완전 정렬, 0 = 무작위)
```

### 플래너 설정

```sql
-- 랜덤 페이지 읽기 비용 (기본: 4.0)
SET random_page_cost = 1.1;
-- SSD는 랜덤 읽기가 빠름 → 낮게 설정
-- HDD는 4.0 유지

-- 순차 페이지 읽기 비용 (기본: 1.0)
SET seq_page_cost = 1.0;

-- 인덱스 스캔을 더 선호하게 만듦
SET enable_seqscan = off;  -- ⚠️ 테스트 용도만!
```

## 15.7 실전 최적화 시나리오

### 시나리오 1: 게시글 목록 조회

```sql
-- 쿼리: 발행된 글, 최신순, 페이지네이션
SELECT id, title, user_id, view_count, created_at
FROM posts
WHERE status = 'published'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- ❌ 인덱스 없음
EXPLAIN ANALYZE SELECT ...;
-- Seq Scan on posts (cost=0.00..50000 rows=100000)
-- Sort (cost=12000..13000)
-- Execution Time: 250 ms

-- ✅ 최적화 1: 기본 인덱스
CREATE INDEX idx_posts_status_created
ON posts(status, created_at DESC);

EXPLAIN ANALYZE SELECT ...;
-- Index Scan using idx_posts_status_created
-- Execution Time: 5 ms  ← 50배 빠름!

-- ✅ 최적화 2: 커버링 인덱스
CREATE INDEX idx_posts_status_created_covering
ON posts(status, created_at DESC)
INCLUDE (id, title, user_id, view_count);

EXPLAIN ANALYZE SELECT ...;
-- Index Only Scan using idx_posts_status_created_covering
-- Execution Time: 2 ms  ← 125배 빠름!
```

### 시나리오 2: 복잡한 필터링

```sql
-- 쿼리: 전자상거래 상품 검색
SELECT *
FROM products
WHERE category_id = 10
  AND price BETWEEN 10000 AND 50000
  AND is_active = true
ORDER BY created_at DESC
LIMIT 20;

-- ❌ 인덱스 없음
-- Execution Time: 400 ms

-- ❌ 잘못된 인덱스
CREATE INDEX idx_bad ON products(price, category_id);
-- price가 범위 조건 → 먼저 오면 안 됨!

-- ✅ 올바른 인덱스
CREATE INDEX idx_products_category_active_price_created
ON products(category_id, is_active, price, created_at DESC);
-- 1. category_id (=)
-- 2. is_active (=)
-- 3. price (범위)
-- 4. created_at (정렬)

EXPLAIN ANALYZE SELECT ...;
-- Index Scan using idx_products_category_active_price_created
-- Execution Time: 3 ms  ← 130배 빠름!
```

### 시나리오 3: JOIN 최적화

```sql
-- 쿼리: 사용자 + 주문 조회
SELECT
  u.name,
  u.email,
  o.id AS order_id,
  o.total_amount,
  o.created_at
FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE u.country = 'Korea'
  AND o.created_at >= '2024-01-01'
ORDER BY o.created_at DESC
LIMIT 100;

-- ❌ 인덱스 없음
-- Execution Time: 800 ms
-- Hash Join + Seq Scan

-- ✅ 최적화
-- 1. users.country 인덱스
CREATE INDEX idx_users_country ON users(country);

-- 2. orders.user_id, created_at 인덱스 (JOIN + 정렬)
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);

EXPLAIN ANALYZE SELECT ...;
-- Nested Loop
--   -> Index Scan on users (idx_users_country)
--   -> Index Scan on orders (idx_orders_user_created)
-- Execution Time: 15 ms  ← 50배 빠름!
```

### 시나리오 4: 집계 쿼리

```sql
-- 쿼리: 사용자별 주문 수
SELECT
  user_id,
  COUNT(*) AS order_count,
  SUM(total_amount) AS total_spent
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY user_id;

-- ❌ 인덱스 없음
-- Seq Scan + HashAggregate
-- Execution Time: 600 ms

-- ✅ 최적화
CREATE INDEX idx_orders_created_user ON orders(created_at, user_id);

EXPLAIN ANALYZE SELECT ...;
-- Index Scan using idx_orders_created_user
-- GroupAggregate
-- Execution Time: 80 ms  ← 7배 빠름!

-- 더 최적화: 커버링 인덱스
CREATE INDEX idx_orders_created_user_covering
ON orders(created_at, user_id)
INCLUDE (total_amount);

EXPLAIN ANALYZE SELECT ...;
-- Index Only Scan using idx_orders_created_user_covering
-- Execution Time: 30 ms  ← 20배 빠름!
```

## 15.8 인덱스 Bloat 관리

### Bloat란?

```
인덱스 Bloat:
UPDATE/DELETE로 인해 인덱스에 쓸모없는 공간이 쌓이는 현상

비유: 책장의 빈 공간
┌─────────────────────────────────┐
│ ❌ Bloat 있음:                  │
│ [책][빈공간][책][빈공간][책]    │
│ → 공간 낭비, 검색 느림          │
│                                 │
│ ✅ Bloat 없음:                  │
│ [책][책][책][책][책]            │
│ → 공간 효율, 검색 빠름          │
└─────────────────────────────────┘
```

### Bloat 확인

```sql
-- 인덱스 크기 확인
SELECT
  schemaname,
  tablename,
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan,
  idx_tup_read
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

--  tablename | indexname        | index_size | idx_scan
-- -----------+------------------+------------+----------
--  users     | users_pkey       | 50 MB      | 1000000
--  users     | idx_users_email  | 45 MB      | 500000
--                                ↑ 예상: 30MB → bloat 의심
```

### REINDEX로 해결

```sql
-- 인덱스 재생성 (bloat 제거)
REINDEX INDEX idx_users_email;

-- 동시 재생성 (LOCK 없이)
REINDEX INDEX CONCURRENTLY idx_users_email;

-- 테이블의 모든 인덱스
REINDEX TABLE users;

-- 동시 재생성
REINDEX TABLE CONCURRENTLY users;

-- 확인
SELECT pg_size_pretty(pg_relation_size('idx_users_email'));
-- 45 MB → 30 MB (15MB 절약!)
```

### VACUUM으로 예방

```sql
-- 정기적인 VACUUM
VACUUM ANALYZE users;

-- 자동 VACUUM 설정 확인
SHOW autovacuum;
-- on

-- 테이블별 VACUUM 통계
SELECT
  schemaname,
  tablename,
  last_vacuum,
  last_autovacuum,
  n_dead_tup
FROM pg_stat_user_tables
WHERE schemaname = 'public';

-- n_dead_tup이 많으면 VACUUM 필요
```

## 15.9 파티셔닝과 인덱스

### 파티션 테이블 인덱스

```sql
-- 파티션 테이블 (시계열 데이터)
CREATE TABLE logs (
  id BIGSERIAL,
  user_id INT NOT NULL,
  action VARCHAR(100) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- 파티션 생성
CREATE TABLE logs_2024_01 PARTITION OF logs
FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE logs_2024_02 PARTITION OF logs
FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- 각 파티션에 인덱스 자동 생성
CREATE INDEX idx_logs_user_created ON logs(user_id, created_at);

-- 확인
\d logs_2024_01
-- Indexes:
--   "logs_2024_01_user_id_created_at_idx" btree (user_id, created_at)

\d logs_2024_02
-- Indexes:
--   "logs_2024_02_user_id_created_at_idx" btree (user_id, created_at)

-- 쿼리 (자동으로 파티션 프루닝)
EXPLAIN SELECT * FROM logs
WHERE created_at >= '2024-01-15'
  AND created_at < '2024-01-20';

-- Index Scan on logs_2024_01
-- → 2024_02 파티션은 검색 안 함!
```

## 15.11 인덱스 체크리스트

### 인덱스 추가 체크리스트

```
✅ 추가해야 할 인덱스:
□ PRIMARY KEY, FOREIGN KEY 컬럼
□ WHERE 절에 자주 사용되는 컬럼 (선택도 > 1%)
□ JOIN 조건 컬럼
□ ORDER BY 컬럼
□ GROUP BY 컬럼
□ UNIQUE 제약조건 컬럼

❌ 추가하면 안 되는 인덱스:
□ 작은 테이블 (< 1000건)
□ 선택도 매우 낮은 컬럼 (성별, 불린 등)
□ 자주 UPDATE/DELETE되는 컬럼
□ 거의 조회 안 되는 컬럼
□ 중복 인덱스
```

### 복합 인덱스 체크리스트

```
✅ 컬럼 순서:
□ 1순위: 등호(=) 조건
□ 2순위: 범위(>, <, BETWEEN) 조건
□ 3순위: ORDER BY 컬럼

✅ 예:
WHERE a = ? AND b > ? ORDER BY c
→ INDEX(a, b, c)

WHERE a = ? AND b = ? AND c > ?
→ INDEX(a, b, c)
```

### 성능 확인 체크리스트

```
✅ 확인 항목:
□ EXPLAIN ANALYZE로 실행 계획 확인
□ Index Scan / Index Only Scan 사용?
□ 실행 시간 < 100ms?
□ 인덱스 크기 확인
□ 인덱스 사용 통계 확인 (idx_scan)
□ Bloat 확인 및 REINDEX
```

## 15.12 실전 예제: 전체 최적화 과정

### 1단계: 현재 상태 확인

```sql
-- 느린 쿼리
SELECT
  u.name,
  u.email,
  COUNT(p.id) AS post_count,
  MAX(p.created_at) AS last_post
FROM users u
LEFT JOIN posts p ON u.id = p.user_id
WHERE u.country = 'Korea'
  AND u.is_active = true
GROUP BY u.id, u.name, u.email
ORDER BY post_count DESC
LIMIT 10;

-- EXPLAIN ANALYZE
EXPLAIN ANALYZE SELECT ...;

-- Hash Join (cost=50000..120000 rows=5000)
--   -> Seq Scan on users (cost=0.00..30000)
--   -> Hash (cost=20000..20000)
--     -> Seq Scan on posts (cost=0.00..20000)
-- Execution Time: 850 ms  ← 느림!
```

### 2단계: 인덱스 추가

```sql
-- 1. users.country, is_active
CREATE INDEX idx_users_country_active ON users(country, is_active);

-- 2. posts.user_id (JOIN)
CREATE INDEX idx_posts_user_id ON posts(user_id);

-- 3. posts.created_at (MAX)
CREATE INDEX idx_posts_user_created ON posts(user_id, created_at DESC);
```

### 3단계: 재확인

```sql
EXPLAIN ANALYZE SELECT ...;

-- Nested Loop Left Join (cost=0.42..8000 rows=5000)
--   -> Index Scan on users (idx_users_country_active)
--   -> Index Scan on posts (idx_posts_user_created)
-- Execution Time: 45 ms  ← 18배 빠름!
```

### 4단계: 통계 업데이트

```sql
ANALYZE users;
ANALYZE posts;
```

### 5단계: 모니터링

```sql
-- 인덱스 사용 통계
SELECT
  indexname,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
WHERE tablename IN ('users', 'posts')
ORDER BY idx_scan DESC;

--  indexname                    | idx_scan
-- ------------------------------+----------
--  idx_users_country_active     | 150000   ✅ 많이 사용
--  idx_posts_user_created       | 80000    ✅ 많이 사용
--  idx_posts_user_id            | 0        ❌ 사용 안 됨 → 삭제 고려
```

## 핵심 요약

### 인덱스 최적화 원칙

```
1. 선택도가 높은 컬럼에 인덱스
   - email, id: ✅
   - gender, boolean: ❌

2. 복합 인덱스 순서
   - 등호(=) → 범위(>, <) → 정렬(ORDER BY)

3. 커버링 인덱스 활용
   - 쿼리의 모든 컬럼을 인덱스에 포함
   - Index Only Scan → 빠름!

4. 불필요한 인덱스 제거
   - 사용하지 않는 인덱스 (idx_scan = 0)
   - 중복 인덱스

5. 정기적인 유지보수
   - VACUUM ANALYZE
   - REINDEX (bloat 제거)
```

### 최적화 프로세스

```
1. EXPLAIN ANALYZE로 느린 쿼리 찾기
2. 적절한 인덱스 추가
3. 실행 계획 재확인
4. 통계 업데이트 (ANALYZE)
5. 모니터링 (pg_stat_user_indexes)
```

### 스캔 방식

```
Index Only Scan    - 가장 빠름 (커버링 인덱스)
Index Scan         - 빠름 (소수 행)
Bitmap Index Scan  - 보통 (중간 행)
Seq Scan           - 느림 (많은 행 또는 인덱스 없음)
```
