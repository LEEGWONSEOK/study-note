# Chapter 14. 인덱스 기초

## 14.1 인덱스란?

### 정의

```
인덱스 (Index):
데이터를 빠르게 찾기 위한 자료구조

비유: 책의 색인 (Index)
┌─────────────────────────────────┐
│ 책 (1000페이지)                 │
├─────────────────────────────────┤
│ ❌ 색인 없이 찾기:              │
│    1페이지부터 1000페이지까지   │
│    순차적으로 찾기 → 오래 걸림  │
│                                 │
│ ✅ 색인으로 찾기:               │
│    "PostgreSQL" → 345페이지     │
│    바로 찾기 → 빠름!            │
└─────────────────────────────────┘

데이터베이스 인덱스 = 책의 색인
```

### 인덱스가 없을 때 vs 있을 때

```sql
-- 100만 건의 데이터
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255),
  name VARCHAR(100),
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 100만 건 삽입 (예시)
INSERT INTO users (email, name)
SELECT
  'user' || i || '@example.com',
  'User ' || i
FROM generate_series(1, 1000000) AS i;


-- ❌ 인덱스 없이 검색
SELECT * FROM users WHERE email = 'user500000@example.com';
-- Seq Scan on users (cost=0.00..25833.00 rows=1 width=...)
-- Planning Time: 0.1 ms
-- Execution Time: 150.5 ms
-- → 100만 건을 모두 읽음!


-- ✅ 인덱스 추가
CREATE INDEX idx_users_email ON users(email);

-- 같은 쿼리
SELECT * FROM users WHERE email = 'user500000@example.com';
-- Index Scan using idx_users_email (cost=0.42..8.44 rows=1 width=...)
-- Planning Time: 0.2 ms
-- Execution Time: 0.3 ms
-- → 인덱스로 바로 찾음! 500배 빠름!
```

### 인덱스가 필요한 경우

```
✅ 인덱스 추가해야 할 때:
- WHERE 절에 자주 사용되는 컬럼
- JOIN 조건에 사용되는 컬럼
- ORDER BY에 사용되는 컬럼
- GROUP BY에 사용되는 컬럼
- FOREIGN KEY 컬럼

❌ 인덱스 불필요한 경우:
- 테이블이 작음 (수천 건 이하)
- 컬럼 값이 거의 동일 (성별: M/F)
- INSERT/UPDATE가 매우 빈번한 테이블
- SELECT가 거의 없는 테이블
```

## 14.2 인덱스 종류

### B-Tree 인덱스 (기본, 가장 일반적)

```sql
-- 기본 인덱스 (자동으로 B-Tree)
CREATE INDEX idx_users_email ON users(email);

-- 명시적으로 B-Tree 지정
CREATE INDEX idx_users_email ON users USING btree(email);

-- 사용 예:
-- - WHERE email = '...'
-- - WHERE email > '...'
-- - WHERE email BETWEEN '...' AND '...'
-- - ORDER BY email
```

**특징:**
- 가장 일반적, 90% 이상 사용
- 등호, 부등호, 범위 검색 모두 가능
- 정렬된 데이터 저장 (B-Tree 구조)

### Hash 인덱스

```sql
CREATE INDEX idx_users_email ON users USING hash(email);

-- 사용 예:
-- - WHERE email = '...'  (등호만!)
```

**특징:**
- 등호(=) 검색만 가능
- 범위 검색, 정렬 불가
- PostgreSQL 10+에서 안정화
- B-Tree보다 빠르지 않아서 거의 사용 안 함

### GiST 인덱스 (Generalized Search Tree)

```sql
CREATE INDEX idx_posts_content ON posts USING gist(content gist_trgm_ops);

-- 사용 예:
-- - 전문 검색 (Full Text Search)
-- - 범위 검색 (범위 겹침 체크)
-- - 지리 정보 (PostGIS)
```

**특징:**
- 복잡한 데이터 타입 (범위, 지리 정보, 텍스트)
- EXCLUDE 제약조건에 사용

### GIN 인덱스 (Generalized Inverted Index)

```sql
-- JSONB 인덱스
CREATE INDEX idx_users_metadata ON users USING gin(metadata);

-- 배열 인덱스
CREATE INDEX idx_posts_tags ON posts USING gin(tags);

-- 전문 검색 인덱스
CREATE INDEX idx_posts_search ON posts USING gin(to_tsvector('english', content));

-- 사용 예:
-- - JSONB 검색
-- - 배열 포함 검색
-- - 전문 검색 (Full Text Search)
```

**특징:**
- JSONB, 배열, 전문 검색에 최적화
- 다중 값 컬럼에 적합
- 읽기는 빠르지만 쓰기는 느림

### BRIN 인덱스 (Block Range Index)

```sql
-- 시간순으로 쌓이는 로그 데이터
CREATE INDEX idx_logs_created_at ON logs USING brin(created_at);

-- 사용 예:
-- - WHERE created_at > '...'
-- - 시계열 데이터
```

**특징:**
- 매우 큰 테이블 (수억 건)
- 물리적으로 정렬된 데이터 (시계열 로그 등)
- 인덱스 크기가 매우 작음
- B-Tree보다 느리지만 저장 공간 절약

## 14.3 인덱스 생성과 관리

### 기본 생성

```sql
-- 단일 컬럼 인덱스
CREATE INDEX idx_users_email ON users(email);

-- 인덱스 이름 생략 (자동 생성)
CREATE INDEX ON users(email);
-- 생성된 이름: users_email_idx

-- 고유 인덱스
CREATE UNIQUE INDEX idx_users_email ON users(email);
-- UNIQUE 제약조건과 동일
```

### 복합 인덱스 (Composite Index)

```sql
-- 여러 컬럼을 조합한 인덱스
CREATE INDEX idx_users_country_city ON users(country, city);

-- 사용 가능:
SELECT * FROM users WHERE country = 'Korea' AND city = 'Seoul';  -- ✅
SELECT * FROM users WHERE country = 'Korea';  -- ✅ (첫 번째 컬럼만)

-- 사용 불가:
SELECT * FROM users WHERE city = 'Seoul';  -- ❌ (두 번째 컬럼만)
-- → city에 별도 인덱스 필요
```

**복합 인덱스 순서 규칙:**
```
첫 번째 컬럼: 가장 자주 필터링되는 컬럼
두 번째 컬럼: 그다음으로 자주 사용되는 컬럼

예:
- WHERE country = 'Korea' AND city = 'Seoul'
  → idx(country, city)

- WHERE status = 'active' AND created_at > '...'
  → idx(status, created_at)
```

### 부분 인덱스 (Partial Index)

```sql
-- 활성 사용자만 인덱싱
CREATE INDEX idx_active_users_email ON users(email)
WHERE is_active = true;

-- 최근 1년 데이터만
CREATE INDEX idx_recent_orders ON orders(created_at)
WHERE created_at >= NOW() - INTERVAL '1 year';

-- NULL이 아닌 것만
CREATE INDEX idx_users_phone ON users(phone)
WHERE phone IS NOT NULL;
```

**장점:**
- 인덱스 크기 감소
- 쓰기 성능 향상
- 자주 쿼리하는 데이터만 빠르게

### 표현식 인덱스 (Expression Index)

```sql
-- 소문자로 검색
CREATE INDEX idx_users_email_lower ON users(LOWER(email));

SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- 인덱스 사용!

-- 날짜 부분만
CREATE INDEX idx_orders_date ON orders(DATE(created_at));

SELECT * FROM orders WHERE DATE(created_at) = '2024-01-15';
-- 인덱스 사용!

-- JSON 필드
CREATE INDEX idx_users_age ON users((metadata->>'age')::INT);

SELECT * FROM users WHERE (metadata->>'age')::INT > 30;
-- 인덱스 사용!
```

### 인덱스 삭제

```sql
-- 인덱스 삭제
DROP INDEX idx_users_email;

-- IF EXISTS 사용
DROP INDEX IF EXISTS idx_users_email;

-- 동시 삭제 (LOCK 없이)
DROP INDEX CONCURRENTLY idx_users_email;
```

### 인덱스 재생성

```sql
-- 기존 인덱스 재생성 (조각 모음)
REINDEX INDEX idx_users_email;

-- 테이블의 모든 인덱스 재생성
REINDEX TABLE users;

-- 동시 재생성 (PostgreSQL 12+)
REINDEX INDEX CONCURRENTLY idx_users_email;
```

## 14.4 CONCURRENTLY 옵션

### 일반 인덱스 생성의 문제

```sql
-- ❌ 일반 생성: 테이블 LOCK!
CREATE INDEX idx_users_email ON users(email);
-- 테이블이 LOCK되어 INSERT/UPDATE 불가
-- 대용량 테이블에서는 수 분~수 시간 소요
```

### CONCURRENTLY로 해결

```sql
-- ✅ 동시 생성: LOCK 없이 생성
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
-- INSERT/UPDATE 계속 가능
-- 시간은 더 걸리지만 서비스 중단 없음
```

**주의사항:**
```sql
-- CONCURRENTLY는 트랜잭션 안에서 사용 불가
BEGIN;
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);  -- ❌ ERROR
COMMIT;

-- 트랜잭션 밖에서 실행해야 함
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);  -- ✅
```

**실전 권장:**
```
운영 환경 (프로덕션):
→ 항상 CONCURRENTLY 사용

개발/테스트 환경:
→ 일반 생성 (빠름)
```

## 14.5 인덱스 조회

### 테이블의 인덱스 확인

```sql
-- psql에서
\d users

-- 출력:
-- Indexes:
--   "users_pkey" PRIMARY KEY, btree (id)
--   "users_email_key" UNIQUE CONSTRAINT, btree (email)
--   "idx_users_name" btree (name)


-- SQL로 조회
SELECT
  tablename,
  indexname,
  indexdef
FROM pg_indexes
WHERE tablename = 'users';

--  tablename | indexname        | indexdef
-- -----------+------------------+-----------------------------------
--  users     | users_pkey       | CREATE UNIQUE INDEX users_pkey...
--  users     | users_email_key  | CREATE UNIQUE INDEX users_email_key...
--  users     | idx_users_name   | CREATE INDEX idx_users_name ON users...
```

### 인덱스 크기 확인

```sql
-- 인덱스 크기
SELECT
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

--  indexname        | size
-- ------------------+--------
--  users_pkey       | 21 MB
--  idx_users_email  | 18 MB
--  idx_users_name   | 15 MB
```

### 인덱스 사용 통계

```sql
-- 인덱스 사용 빈도
SELECT
  schemaname,
  tablename,
  indexname,
  idx_scan AS scans,
  idx_tup_read AS tuples_read,
  idx_tup_fetch AS tuples_fetched
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan DESC;

--  tablename | indexname        | scans  | tuples_read | tuples_fetched
-- -----------+------------------+--------+-------------+----------------
--  users     | users_pkey       | 150000 | 150000      | 150000
--  users     | idx_users_email  | 80000  | 80000       | 80000
--  users     | idx_users_name   | 0      | 0           | 0
--                                 ↑ 사용 안 됨! 삭제 고려
```

### 사용하지 않는 인덱스 찾기

```sql
-- 한 번도 사용 안 된 인덱스
SELECT
  schemaname,
  tablename,
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND schemaname = 'public'
  AND indexrelid NOT IN (
    SELECT conindid FROM pg_constraint WHERE contype IN ('p', 'u')
    -- PRIMARY KEY, UNIQUE는 제외
  )
ORDER BY pg_relation_size(indexrelid) DESC;
```

## 14.6 EXPLAIN으로 인덱스 확인

### 기본 사용

```sql
-- 실행 계획만 확인 (실제 실행 X)
EXPLAIN
SELECT * FROM users WHERE email = 'alice@example.com';

-- 출력:
-- Seq Scan on users (cost=0.00..25833.00 rows=1 width=45)
--   Filter: (email = 'alice@example.com')
-- → 순차 스캔 (인덱스 미사용)


-- 인덱스 추가 후
CREATE INDEX idx_users_email ON users(email);

EXPLAIN
SELECT * FROM users WHERE email = 'alice@example.com';

-- 출력:
-- Index Scan using idx_users_email on users (cost=0.42..8.44 rows=1 width=45)
--   Index Cond: (email = 'alice@example.com')
-- → 인덱스 스캔!
```

### EXPLAIN ANALYZE

```sql
-- 실제 실행 + 통계
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'alice@example.com';

-- 출력:
-- Index Scan using idx_users_email on users (cost=0.42..8.44 rows=1 width=45)
--                                           (actual time=0.025..0.026 rows=1 loops=1)
--   Index Cond: (email = 'alice@example.com')
-- Planning Time: 0.123 ms
-- Execution Time: 0.045 ms
-- → 실제 0.045ms 소요!
```

### 스캔 방식 이해

```sql
-- Seq Scan (순차 스캔)
EXPLAIN SELECT * FROM users WHERE age > 20;
-- Seq Scan on users
-- → 인덱스 없거나 대부분 데이터 읽을 때

-- Index Scan (인덱스 스캔)
EXPLAIN SELECT * FROM users WHERE id = 100;
-- Index Scan using users_pkey
-- → PRIMARY KEY 사용

-- Index Only Scan (인덱스만 스캔)
EXPLAIN SELECT email FROM users WHERE email = 'alice@example.com';
-- Index Only Scan using idx_users_email
-- → 인덱스에 필요한 모든 데이터 있음

-- Bitmap Index Scan (비트맵 스캔)
EXPLAIN SELECT * FROM users WHERE age > 20 AND country = 'Korea';
-- Bitmap Heap Scan on users
--   Recheck Cond: (age > 20 AND country = 'Korea')
--   -> Bitmap Index Scan on idx_users_age
-- → 여러 인덱스 조합
```

## 14.7 실전 예제

### 블로그 시스템

```sql
-- 테이블 생성
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  username VARCHAR(50) UNIQUE NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  user_id INT NOT NULL REFERENCES users(id),
  title VARCHAR(255) NOT NULL,
  content TEXT NOT NULL,
  status VARCHAR(20) DEFAULT 'draft',
  view_count INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  published_at TIMESTAMPTZ
);

CREATE TABLE comments (
  id SERIAL PRIMARY KEY,
  post_id INT NOT NULL REFERENCES posts(id),
  user_id INT NOT NULL REFERENCES users(id),
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);


-- 필수 인덱스
-- 1. FOREIGN KEY 컬럼
CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_comments_post_id ON comments(post_id);
CREATE INDEX idx_comments_user_id ON comments(user_id);

-- 2. WHERE 절에 자주 사용
CREATE INDEX idx_posts_status ON posts(status);

-- 3. ORDER BY에 자주 사용
CREATE INDEX idx_posts_created_at ON posts(created_at DESC);
CREATE INDEX idx_comments_created_at ON comments(created_at DESC);

-- 4. 복합 인덱스 (상태 + 발행일)
CREATE INDEX idx_posts_status_published ON posts(status, published_at DESC);

-- 5. 부분 인덱스 (발행된 글만)
CREATE INDEX idx_published_posts ON posts(published_at DESC)
WHERE status = 'published';
```

### 전자상거래 시스템

```sql
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  category_id INT NOT NULL,
  name VARCHAR(255) NOT NULL,
  price NUMERIC(10, 2) NOT NULL,
  stock INT DEFAULT 0,
  is_active BOOLEAN DEFAULT true,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INT NOT NULL,
  status VARCHAR(20) NOT NULL,
  total_amount NUMERIC(10, 2) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE order_items (
  order_id INT NOT NULL,
  product_id INT NOT NULL,
  quantity INT NOT NULL,
  price NUMERIC(10, 2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);


-- 필수 인덱스
-- 1. 카테고리별 상품 검색
CREATE INDEX idx_products_category ON products(category_id)
WHERE is_active = true;

-- 2. 가격 범위 검색
CREATE INDEX idx_products_price ON products(price)
WHERE is_active = true;

-- 3. 주문 조회 (사용자별, 최신순)
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);

-- 4. 주문 상태별 조회
CREATE INDEX idx_orders_status_created ON orders(status, created_at DESC);

-- 5. FOREIGN KEY
CREATE INDEX idx_order_items_product ON order_items(product_id);
```

### 검색 기능

```sql
-- 전문 검색 (Full Text Search)
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  title VARCHAR(255) NOT NULL,
  content TEXT NOT NULL,
  search_vector tsvector
);

-- 검색 벡터 자동 업데이트
CREATE TRIGGER posts_search_update
BEFORE INSERT OR UPDATE ON posts
FOR EACH ROW EXECUTE FUNCTION
  tsvector_update_trigger(search_vector, 'pg_catalog.english', title, content);

-- GIN 인덱스 생성
CREATE INDEX idx_posts_search ON posts USING gin(search_vector);

-- 검색
SELECT * FROM posts
WHERE search_vector @@ to_tsquery('english', 'postgresql & performance');
-- 인덱스 사용!
```

## 14.8 인덱스 안티패턴

### 1. 너무 많은 인덱스

```sql
-- ❌ 나쁜 예: 모든 컬럼에 인덱스
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255),
  name VARCHAR(100),
  age INT,
  country VARCHAR(50),
  city VARCHAR(50),
  created_at TIMESTAMPTZ
);

CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_name ON users(name);
CREATE INDEX idx_users_age ON users(age);
CREATE INDEX idx_users_country ON users(country);
CREATE INDEX idx_users_city ON users(city);
CREATE INDEX idx_users_created_at ON users(created_at);
-- 문제: INSERT/UPDATE 느려짐, 저장 공간 낭비

-- ✅ 좋은 예: 자주 쿼리하는 컬럼만
CREATE INDEX idx_users_email ON users(email);  -- WHERE, JOIN
CREATE INDEX idx_users_country_city ON users(country, city);  -- WHERE
CREATE INDEX idx_users_created_at ON users(created_at DESC);  -- ORDER BY
```

### 2. 함수 사용 시 인덱스 미사용

```sql
-- ❌ 인덱스 미사용
CREATE INDEX idx_users_email ON users(email);

SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- Seq Scan (인덱스 안 씀!)

-- ✅ 표현식 인덱스 생성
CREATE INDEX idx_users_email_lower ON users(LOWER(email));

SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- Index Scan (인덱스 사용!)
```

### 3. OR 조건

```sql
-- ❌ 인덱스 미사용 (OR)
SELECT * FROM users WHERE email = 'alice@ex.com' OR name = 'Alice';
-- Seq Scan

-- ✅ UNION 사용
SELECT * FROM users WHERE email = 'alice@ex.com'
UNION
SELECT * FROM users WHERE name = 'Alice';
-- Index Scan 각각 사용
```

### 4. LIKE 패턴

```sql
-- ✅ 인덱스 사용
SELECT * FROM users WHERE email LIKE 'alice%';
-- Index Scan (시작 부분 매칭)

-- ❌ 인덱스 미사용
SELECT * FROM users WHERE email LIKE '%alice%';
-- Seq Scan (중간 매칭)

-- 중간 매칭이 필요하면 전문 검색 사용
CREATE INDEX idx_users_email_trgm ON users USING gin(email gin_trgm_ops);
CREATE EXTENSION IF NOT EXISTS pg_trgm;

SELECT * FROM users WHERE email LIKE '%alice%';
-- 이제 인덱스 사용!
```

### 5. NULL 검색

```sql
-- ❌ 인덱스 미사용
CREATE INDEX idx_users_phone ON users(phone);

SELECT * FROM users WHERE phone IS NULL;
-- Seq Scan (B-Tree는 NULL 저장 안 함)

-- ✅ 부분 인덱스
CREATE INDEX idx_users_phone_not_null ON users(phone)
WHERE phone IS NOT NULL;

SELECT * FROM users WHERE phone = '010-1234-5678';
-- Index Scan
```

## 14.9 인덱스 모니터링

### 인덱스 bloat (부풀음) 확인

```sql
-- 인덱스 bloat 비율
SELECT
  schemaname,
  tablename,
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

-- bloat가 심하면 REINDEX
REINDEX INDEX CONCURRENTLY idx_users_email;
```

### 테이블 + 인덱스 전체 크기

```sql
SELECT
  tablename,
  pg_size_pretty(pg_total_relation_size(tablename::regclass)) AS total_size,
  pg_size_pretty(pg_relation_size(tablename::regclass)) AS table_size,
  pg_size_pretty(
    pg_total_relation_size(tablename::regclass) - pg_relation_size(tablename::regclass)
  ) AS indexes_size
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(tablename::regclass) DESC;

--  tablename | total_size | table_size | indexes_size
-- -----------+------------+------------+--------------
--  users     | 150 MB     | 100 MB     | 50 MB
--  posts     | 500 MB     | 350 MB     | 150 MB
```

### 인덱스 성능 측정

```sql

SELECT * FROM users WHERE email = 'alice@example.com';
-- Time: 0.5 ms

-- 인덱스 사용 여부 확인
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'alice@example.com';
```

## 14.10 인덱스 전략

### 읽기 vs 쓰기 트레이드오프

```
인덱스 많음:
✅ SELECT 빠름
❌ INSERT/UPDATE/DELETE 느림
❌ 저장 공간 많이 사용

인덱스 적음:
❌ SELECT 느림
✅ INSERT/UPDATE/DELETE 빠름
✅ 저장 공간 절약

균형 맞추기:
- 자주 조회하는 컬럼만 인덱스
- 사용하지 않는 인덱스 삭제
- 복합 인덱스 활용
```

### 인덱스 우선순위

```
1순위: PRIMARY KEY, FOREIGN KEY
2순위: WHERE 절에 자주 사용되는 컬럼
3순위: JOIN 조건 컬럼
4순위: ORDER BY, GROUP BY 컬럼
5순위: 복합 인덱스 (여러 조건 조합)
```

### 복합 인덱스 vs 단일 인덱스

```sql
-- 쿼리
SELECT * FROM posts
WHERE status = 'published'
  AND created_at >= '2024-01-01'
ORDER BY created_at DESC;

-- 방법 1: 복합 인덱스 (권장)
CREATE INDEX idx_posts_status_created ON posts(status, created_at DESC);
-- 한 번의 인덱스 스캔으로 해결

-- 방법 2: 단일 인덱스 2개
CREATE INDEX idx_posts_status ON posts(status);
CREATE INDEX idx_posts_created_at ON posts(created_at DESC);
-- PostgreSQL이 둘 중 하나만 선택하거나 Bitmap Scan 사용
-- 복합 인덱스보다 느림
```

### 부분 인덱스로 최적화

```sql
-- 전체 인덱스
CREATE INDEX idx_posts_created ON posts(created_at DESC);
-- 모든 상태(draft, published, archived) 포함

-- 부분 인덱스 (더 작고 빠름)
CREATE INDEX idx_published_posts_created ON posts(created_at DESC)
WHERE status = 'published';
-- 발행된 글만 (전체의 10%만 인덱싱)

-- 쿼리
SELECT * FROM posts
WHERE status = 'published'
ORDER BY created_at DESC
LIMIT 10;
-- 부분 인덱스 사용!
```

## 14.11 실전 시나리오

### 시나리오 1: 느린 쿼리 최적화

```sql
-- 문제: 느린 쿼리
SELECT * FROM orders
WHERE user_id = 1000
  AND status = 'completed'
ORDER BY created_at DESC
LIMIT 10;

-- Planning Time: 0.5 ms
-- Execution Time: 350.2 ms  ← 느림!

-- 1. EXPLAIN ANALYZE로 확인
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 1000
  AND status = 'completed'
ORDER BY created_at DESC
LIMIT 10;

-- Seq Scan on orders (cost=0.00..50000 rows=500 width=100)
--   Filter: (user_id = 1000 AND status = 'completed')
-- → 순차 스캔!

-- 2. 인덱스 추가
CREATE INDEX idx_orders_user_status_created
ON orders(user_id, status, created_at DESC);

-- 3. 다시 실행
SELECT * FROM orders
WHERE user_id = 1000
  AND status = 'completed'
ORDER BY created_at DESC
LIMIT 10;

-- Index Scan using idx_orders_user_status_created
-- Planning Time: 0.3 ms
-- Execution Time: 0.8 ms  ← 400배 빠름!
```

### 시나리오 2: 중복 인덱스 제거

```sql
-- 현재 인덱스 확인
\d posts

-- Indexes:
--   "posts_pkey" PRIMARY KEY, btree (id)
--   "idx_posts_user_id" btree (user_id)
--   "idx_posts_user_created" btree (user_id, created_at)  ← 이것만 있으면 됨
--   "idx_posts_created" btree (created_at)

-- 중복 제거
DROP INDEX idx_posts_user_id;
-- idx_posts_user_created가 (user_id) 쿼리도 커버 가능!

-- 크기 확인
SELECT
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE tablename = 'posts';

-- 5MB 절약!
```

### 시나리오 3: JSONB 인덱스

```sql
-- 사용자 메타데이터 (JSONB)
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) NOT NULL,
  metadata JSONB
);

-- 예시 데이터
INSERT INTO users (email, metadata) VALUES
('alice@ex.com', '{"age": 25, "country": "Korea", "interests": ["coding", "music"]}'),
('bob@ex.com', '{"age": 30, "country": "USA", "interests": ["gaming"]}');

-- ❌ 느린 쿼리
SELECT * FROM users WHERE metadata->>'country' = 'Korea';
-- Seq Scan

-- ✅ GIN 인덱스
CREATE INDEX idx_users_metadata ON users USING gin(metadata);

SELECT * FROM users WHERE metadata @> '{"country": "Korea"}';
-- Index Scan using idx_users_metadata

-- 또는 특정 키만
CREATE INDEX idx_users_country ON users((metadata->>'country'));

SELECT * FROM users WHERE metadata->>'country' = 'Korea';
-- Index Scan using idx_users_country
```

## 핵심 요약

### 인덱스 종류

```
B-Tree (기본)     - 대부분의 경우 사용
Hash              - 등호 검색만 (거의 사용 안 함)
GiST              - 범위, 지리 정보
GIN               - JSONB, 배열, 전문 검색
BRIN              - 시계열 대용량 데이터
```

### 인덱스 생성

```sql
-- 기본
CREATE INDEX idx_name ON table(column);

-- 복합
CREATE INDEX idx_name ON table(col1, col2);

-- 부분
CREATE INDEX idx_name ON table(column) WHERE condition;

-- 표현식
CREATE INDEX idx_name ON table(LOWER(column));

-- 동시 생성 (운영 환경)
CREATE INDEX CONCURRENTLY idx_name ON table(column);
```

### 인덱스 모니터링

```sql
-- 인덱스 목록
\d table_name

-- 인덱스 크기
SELECT pg_size_pretty(pg_relation_size('idx_name'));

-- 인덱스 사용 통계
SELECT * FROM pg_stat_user_indexes WHERE tablename = 'table_name';

-- 실행 계획
EXPLAIN ANALYZE SELECT ...
```

### 권장 사항

```
✅ 해야 할 것:
- PRIMARY KEY, FOREIGN KEY 컬럼
- WHERE, JOIN 자주 사용되는 컬럼
- 복합 인덱스로 여러 조건 커버
- CONCURRENTLY로 운영 환경 인덱스 생성
- 사용하지 않는 인덱스 삭제

❌ 하지 말아야 할 것:
- 모든 컬럼에 인덱스
- 작은 테이블 (수천 건)에 인덱스
- 거의 동일한 값(성별 등)에 인덱스
- 중복 인덱스
```
