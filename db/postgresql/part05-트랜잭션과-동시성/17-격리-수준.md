# Chapter 17. 격리 수준

## 17.1 격리 수준이란?

### 정의

```
격리 수준 (Isolation Level):
동시에 실행되는 트랜잭션들이 서로 어느 정도 독립적으로 실행되는지 정의

비유: 도서관 열람실
┌─────────────────────────────────┐
│ 1인실 (Serializable)            │
│ - 완전히 독립                   │
│ - 다른 사람 영향 없음           │
│ - 가장 느림                     │
├─────────────────────────────────┤
│ 칸막이 (Repeatable Read)        │
│ - 옆 사람 보이지만 집중 가능    │
│ - 중간 속도                     │
├─────────────────────────────────┤
│ 오픈 공간 (Read Committed)      │
│ - 다른 사람 보임                │
│ - 가장 빠름                     │
└─────────────────────────────────┘

격리 수준 ↑ → 안전성 ↑, 성능 ↓
격리 수준 ↓ → 안전성 ↓, 성능 ↑
```

### 읽기 이상 현상

```
Dirty Read (더티 리드):
커밋되지 않은 데이터를 읽음

Non-Repeatable Read (반복 불가능 읽기):
같은 트랜잭션에서 같은 데이터를 다시 읽었을 때 값이 다름

Phantom Read (팬텀 리드):
같은 트랜잭션에서 같은 조건 조회 시 결과 행이 다름
```

---

## 17.2 Read Uncommitted

### 정의

```
Read Uncommitted:
커밋되지 않은 데이터도 읽을 수 있음

⚠️ PostgreSQL은 지원하지 않음
(설정해도 Read Committed로 동작)
```

### Dirty Read 문제

```sql
-- MySQL 등 다른 DBMS에서의 예시
-- PostgreSQL은 이 문제를 허용하지 않음!

-- 세션 1
BEGIN;
UPDATE accounts SET balance = 5000 WHERE id = 1;
-- 아직 커밋 안 됨

-- 세션 2 (Read Uncommitted)
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT balance FROM accounts WHERE id = 1;
-- 5000 (커밋 안 된 데이터!)

-- 세션 1
ROLLBACK;  -- 취소!

-- 세션 2가 읽은 5000은 유령 데이터!
```

### PostgreSQL에서

```sql
-- Read Uncommitted 설정해도
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- 실제로는 Read Committed로 동작
SHOW transaction_isolation;
-- read committed

-- PostgreSQL은 Dirty Read를 절대 허용하지 않음!
```

## 17.3 Read Committed (기본값)

### 정의

```
Read Committed:
커밋된 데이터만 읽을 수 있음

PostgreSQL 기본값 ⭐
가장 일반적으로 사용
```

### 특징

```sql
-- 세션 1
BEGIN;
UPDATE accounts SET balance = 5000 WHERE id = 1;
-- 아직 커밋 안 됨

-- 세션 2
SELECT balance FROM accounts WHERE id = 1;
-- 10000 (커밋된 이전 값)

-- 세션 1
COMMIT;

-- 세션 2
SELECT balance FROM accounts WHERE id = 1;
-- 5000 (커밋된 새 값)

특징:
✅ Dirty Read 방지
❌ Non-Repeatable Read 발생
❌ Phantom Read 발생
```

### Non-Repeatable Read 예제

```sql
-- 세션 1: 조회
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- 10000

-- 세션 2: 업데이트
BEGIN;
UPDATE accounts SET balance = 5000 WHERE id = 1;
COMMIT;

-- 세션 1: 다시 조회
SELECT balance FROM accounts WHERE id = 1;
-- 5000 (값이 바뀜!)

COMMIT;

-- 같은 트랜잭션에서 같은 데이터를 읽었는데 값이 다름
-- → Non-Repeatable Read
```

### Phantom Read 예제

```sql
-- 세션 1: 조회
BEGIN;
SELECT COUNT(*) FROM users WHERE age >= 20;
-- 100명

-- 세션 2: 삽입
BEGIN;
INSERT INTO users (name, age) VALUES ('Alice', 25);
COMMIT;

-- 세션 1: 다시 조회
SELECT COUNT(*) FROM users WHERE age >= 20;
-- 101명 (행이 추가됨!)

COMMIT;

-- 같은 조건으로 조회했는데 결과가 다름
-- → Phantom Read
```

### 언제 사용?

```
✅ 대부분의 경우에 적합
- 일반적인 웹 애플리케이션
- 조회 위주 서비스
- 성능이 중요한 경우

❌ 부적합한 경우
- 금융 거래 (정확한 잔액 계산)
- 보고서 생성 (일관된 스냅샷 필요)
- 통계 계산
```

## 17.4 Repeatable Read

### 정의

```
Repeatable Read:
트랜잭션 시작 시점의 스냅샷을 읽음

PostgreSQL의 Repeatable Read:
- MVCC (Multi-Version Concurrency Control) 사용
- 스냅샷 격리 (Snapshot Isolation)
- Phantom Read도 사실상 방지!
```

### 기본 동작

```sql
-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
-- 10000

-- 세션 2
BEGIN;
UPDATE accounts SET balance = 5000 WHERE id = 1;
COMMIT;

-- 세션 1: 다시 조회
SELECT balance FROM accounts WHERE id = 1;
-- 10000 (여전히 이전 값! 스냅샷 유지)

COMMIT;

-- 트랜잭션 종료 후
SELECT balance FROM accounts WHERE id = 1;
-- 5000 (이제 새 값)
```

### Phantom Read 방지

```sql
-- PostgreSQL의 Repeatable Read는 Phantom Read도 방지!

-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM users WHERE age >= 20;
-- 100명

-- 세션 2
BEGIN;
INSERT INTO users (name, age) VALUES ('Alice', 25);
COMMIT;

-- 세션 1: 다시 조회
SELECT COUNT(*) FROM users WHERE age >= 20;
-- 100명 (여전히! PostgreSQL의 스냅샷 격리)

COMMIT;

-- 트랜잭션 종료 후
SELECT COUNT(*) FROM users WHERE age >= 20;
-- 101명
```

### Serialization 에러

```sql
-- 쓰기-쓰기 충돌 시 에러 발생

-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
-- 10000

-- 세션 2
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
-- 10000

-- 세션 1
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
-- 9000
COMMIT;

-- 세션 2
UPDATE accounts SET balance = balance - 2000 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update

ROLLBACK;

-- 재시도 필요!
```

### 재시도 패턴

```sql
-- 애플리케이션 레벨에서 재시도
DO $$
DECLARE
  max_retries INT := 3;
  retry_count INT := 0;
  success BOOLEAN := false;
BEGIN
  WHILE NOT success AND retry_count < max_retries LOOP
    BEGIN
      -- 트랜잭션 시작
      SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

      -- 작업 수행
      UPDATE accounts SET balance = balance - 1000 WHERE id = 1;

      success := true;
      COMMIT;
    EXCEPTION
      WHEN serialization_failure THEN
        ROLLBACK;
        retry_count := retry_count + 1;
        RAISE NOTICE 'Retry %', retry_count;
        PERFORM pg_sleep(0.1);  -- 0.1초 대기
    END;
  END LOOP;

  IF NOT success THEN
    RAISE EXCEPTION 'Failed after % retries', max_retries;
  END IF;
END $$;
```

### 언제 사용?

```
✅ 적합한 경우
- 보고서 생성 (일관된 스냅샷)
- 통계 계산
- 배치 작업
- 재고 관리

❌ 부적합한 경우
- 높은 동시성 쓰기 작업 (Serialization 에러 빈번)
- 실시간 대시보드
```

## 17.5 Serializable

### 정의

```
Serializable:
완전한 직렬화 (순차 실행과 동일한 결과)

가장 높은 격리 수준
모든 읽기 이상 현상 방지
```

### 기본 동작

```sql
-- 세션 1
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(balance) FROM accounts WHERE user_id = 1;
-- 10000

-- 세션 2
BEGIN ISOLATION LEVEL SERIALIZABLE;
INSERT INTO accounts (user_id, balance) VALUES (1, 5000);
COMMIT;

-- 세션 1: 다시 조회
SELECT SUM(balance) FROM accounts WHERE user_id = 1;
-- 10000 (여전히 이전 값)

-- 세션 1: 업데이트 시도
UPDATE accounts SET balance = balance * 1.1 WHERE user_id = 1;
-- ERROR: could not serialize access due to read/write dependencies

ROLLBACK;
```

### Read-Write Conflict

```sql
-- 읽기-쓰기 충돌 감지

-- 세션 1: 읽기
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM users WHERE age >= 20;
-- 100명

-- 세션 2: 쓰기
BEGIN ISOLATION LEVEL SERIALIZABLE;
INSERT INTO users (name, age) VALUES ('Alice', 25);
COMMIT;

-- 세션 1: 쓰기 (읽은 데이터 기반)
INSERT INTO summary (total_adults, created_at)
VALUES (100, NOW());
-- ERROR: could not serialize access

ROLLBACK;
```

### 언제 사용?

```
✅ 적합한 경우
- 금융 거래 (정확성 최우선)
- 재고 관리 (정확한 재고 추적)
- 회계 시스템

❌ 부적합한 경우
- 대부분의 웹 애플리케이션 (성능 저하)
- 높은 동시성 필요한 경우
```

## 17.6 격리 수준 비교

### 문제 발생 여부

```
격리 수준         | Dirty Read | Non-Repeatable | Phantom Read | 성능
-----------------|------------|----------------|--------------|------
Read Uncommitted | 발생        | 발생            | 발생          | 최상
Read Committed   | 방지        | 발생            | 발생          | 좋음 ⭐
Repeatable Read  | 방지        | 방지            | 방지*         | 보통
Serializable     | 방지        | 방지            | 방지          | 나쁨

* PostgreSQL의 Repeatable Read는 Phantom Read도 방지
```

### PostgreSQL 특징

```
PostgreSQL의 격리 수준:
- Read Uncommitted → Read Committed로 동작
- Read Committed (기본값)
- Repeatable Read (스냅샷 격리, Phantom Read도 방지)
- Serializable (SSI - Serializable Snapshot Isolation)

다른 DBMS와 차이:
- MySQL의 Repeatable Read는 Phantom Read 허용
- PostgreSQL은 MVCC로 더 강력한 격리
```

## 17.7 실전 시나리오

### 시나리오 1: 좌석 예약 (Repeatable Read)

```sql
-- 문제: Read Committed에서 중복 예약 가능
-- 세션 1
BEGIN;
SELECT seat_number FROM seats
WHERE screening_id = 100 AND is_booked = false
LIMIT 1;
-- 'A1'

-- 세션 2
BEGIN;
SELECT seat_number FROM seats
WHERE screening_id = 100 AND is_booked = false
LIMIT 1;
-- 'A1' (같은 좌석!)

-- 세션 1
UPDATE seats SET is_booked = true WHERE seat_number = 'A1';
COMMIT;

-- 세션 2
UPDATE seats SET is_booked = true WHERE seat_number = 'A1';
COMMIT;
-- 중복 예약!


-- 해결: Repeatable Read + FOR UPDATE
-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT seat_number FROM seats
WHERE screening_id = 100 AND is_booked = false
ORDER BY seat_number
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 'A1', LOCK 획득

-- 세션 2
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT seat_number FROM seats
WHERE screening_id = 100 AND is_booked = false
ORDER BY seat_number
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 'A2' (A1은 SKIP)

-- 중복 예약 방지!
```

### 시나리오 2: 재고 관리 (Repeatable Read)

```sql
-- 문제: Lost Update
-- 세션 1
BEGIN;
SELECT stock FROM products WHERE id = 10;
-- stock: 100

-- 세션 2
BEGIN;
SELECT stock FROM products WHERE id = 10;
-- stock: 100

-- 세션 1
UPDATE products SET stock = 100 - 5 WHERE id = 10;
-- stock: 95
COMMIT;

-- 세션 2
UPDATE products SET stock = 100 - 3 WHERE id = 10;
-- stock: 97 (잘못됨! 92여야 함)
COMMIT;


-- 해결: Repeatable Read
-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
UPDATE products SET stock = stock - 5 WHERE id = 10;
COMMIT;

-- 세션 2
BEGIN ISOLATION LEVEL REPEATABLE READ;
UPDATE products SET stock = stock - 3 WHERE id = 10;
-- ERROR: could not serialize access
ROLLBACK;
-- 재시도 필요
```

### 시나리오 3: 보고서 생성 (Repeatable Read)

```sql
-- 문제: 일관되지 않은 스냅샷
-- Read Committed
BEGIN;

-- 사용자 수
SELECT COUNT(*) FROM users;
-- 10000명

-- 중간에 데이터 변경됨
-- (다른 트랜잭션이 1000명 삽입)

-- 주문 수
SELECT COUNT(*) FROM orders;
-- 12000건 (새로 추가된 1000명의 주문 포함)

COMMIT;

-- 사용자당 평균 주문: 12000 / 10000 = 1.2
-- 실제로는 11000명이므로 잘못된 계산!


-- 해결: Repeatable Read
BEGIN ISOLATION LEVEL REPEATABLE READ;

-- 트랜잭션 시작 시점의 스냅샷
SELECT COUNT(*) FROM users;
-- 10000명

SELECT COUNT(*) FROM orders;
-- 11000건 (스냅샷 기준)

COMMIT;

-- 일관된 보고서!
```

### 시나리오 4: 금융 거래 (Serializable)

```sql
-- 계좌 이체 + 수수료
BEGIN ISOLATION LEVEL SERIALIZABLE;

-- 1. 잔액 확인
SELECT balance FROM accounts WHERE id = 1;
-- 10000

-- 2. 이체
UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
UPDATE accounts SET balance = balance + 5000 WHERE id = 2;

-- 3. 수수료 계산 (전체 계좌 합계 기반)
SELECT SUM(balance) INTO total_balance FROM accounts;

-- 4. 수수료 차감
UPDATE accounts SET balance = balance - (total_balance * 0.001)
WHERE id = 1;

COMMIT;

-- Serializable로 다른 트랜잭션 간섭 방지
```

## 17.8 격리 수준 설정

### 세션 레벨 설정

```sql
-- 현재 세션의 기본 격리 수준 변경
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 확인
SHOW default_transaction_isolation;
-- repeatable read

-- 이후 모든 트랜잭션에 적용
BEGIN;
-- Repeatable Read로 시작
SELECT ...;
COMMIT;
```

### 트랜잭션 레벨 설정

```sql
-- 특정 트랜잭션만
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT ...;
COMMIT;

-- 또는
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT ...;
COMMIT;
```

### 데이터베이스 레벨 설정

```sql
-- postgresql.conf
-- default_transaction_isolation = 'repeatable read'

-- 또는 ALTER DATABASE
ALTER DATABASE mydb SET default_transaction_isolation = 'repeatable read';

-- 확인
SELECT name, setting FROM pg_settings
WHERE name = 'default_transaction_isolation';
```

## 17.9 MVCC (Multi-Version Concurrency Control)

### 정의

```
MVCC:
PostgreSQL이 동시성을 관리하는 방식

원리:
- 각 행의 여러 버전을 유지
- 읽기는 스냅샷 읽기
- 쓰기는 새 버전 생성
- VACUUM으로 오래된 버전 정리
```

### 동작 원리

```sql
-- 초기 데이터
INSERT INTO users (id, name) VALUES (1, 'Alice');
-- version 1: (id=1, name='Alice', xmin=100, xmax=NULL)

-- 트랜잭션 1 (xid=101)
BEGIN;
SELECT * FROM users WHERE id = 1;
-- version 1 읽기 (xmax=NULL이므로 유효)

-- 트랜잭션 2 (xid=102)
BEGIN;
UPDATE users SET name = 'Bob' WHERE id = 1;
-- version 2 생성: (id=1, name='Bob', xmin=102, xmax=NULL)
-- version 1 수정: (id=1, name='Alice', xmin=100, xmax=102)
COMMIT;

-- 트랜잭션 1
SELECT * FROM users WHERE id = 1;
-- 여전히 version 1 읽기 ('Alice')
-- xid=101 < xmax=102 이므로 version 1이 유효

COMMIT;

-- 새 트랜잭션 (xid=103)
SELECT * FROM users WHERE id = 1;
-- version 2 읽기 ('Bob')
-- xid=103 >= xmin=102 이므로 version 2가 유효
```

### 시스템 컬럼

```sql
-- 숨겨진 시스템 컬럼 확인
SELECT
  xmin,     -- 생성 트랜잭션 ID
  xmax,     -- 삭제 트랜잭션 ID (0 = 유효)
  cmin,     -- 생성 명령 ID
  cmax,     -- 삭제 명령 ID
  ctid,     -- 물리적 위치
  *
FROM users;

--  xmin | xmax | cmin | cmax | ctid  | id | name
-- ------+------+------+------+-------+----+------
--  100  |  0   |  0   |  0   | (0,1) | 1  | Alice
--  102  |  0   |  0   |  0   | (0,2) | 2  | Bob
```

## 17.10 격리 수준 모니터링

### 현재 격리 수준 확인

```sql
-- 현재 트랜잭션
SHOW transaction_isolation;
-- read committed

-- 세션 기본값
SHOW default_transaction_isolation;
-- read committed

-- 모든 활성 트랜잭션
SELECT
  pid,
  usename,
  state,
  backend_xid,
  backend_xmin
FROM pg_stat_activity
WHERE state = 'active';
```

### Serialization 에러 통계

```sql
-- pg_stat_database
SELECT
  datname,
  xact_commit,
  xact_rollback,
  conflicts,
  deadlocks
FROM pg_stat_database
WHERE datname = 'mydb';

--  datname | xact_commit | xact_rollback | conflicts | deadlocks
-- ---------+-------------+---------------+-----------+-----------
--  mydb    | 1000000     | 5000          | 120       | 5
--                         ↑ 재시도 필요    ↑ Serialization 에러
```

### 충돌 모니터링

```sql
-- 애플리케이션에서 재시도 카운터 추가
CREATE TABLE retry_stats (
  date DATE PRIMARY KEY,
  serialization_errors INT DEFAULT 0,
  deadlocks INT DEFAULT 0
);

-- 재시도 시마다 기록
INSERT INTO retry_stats (date, serialization_errors)
VALUES (CURRENT_DATE, 1)
ON CONFLICT (date) DO UPDATE
SET serialization_errors = retry_stats.serialization_errors + 1;
```

## 17.11 격리 수준 선택 가이드

### 일반 웹 애플리케이션

```sql
-- Read Committed (기본값)
BEGIN;
-- 조회, 단순 업데이트
SELECT * FROM users WHERE id = 1;
UPDATE users SET last_login = NOW() WHERE id = 1;
COMMIT;

✅ 대부분의 경우 충분
✅ 성능 좋음
✅ Serialization 에러 없음
```

### 보고서 / 통계

```sql
-- Repeatable Read
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- 일관된 스냅샷 필요
SELECT COUNT(*) FROM users;
SELECT SUM(total_amount) FROM orders;
COMMIT;

✅ 일관된 데이터
✅ Phantom Read 방지
```

### 재고 / 좌석 예약

```sql
-- Repeatable Read + FOR UPDATE
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM products WHERE id = 10 FOR UPDATE;
UPDATE products SET stock = stock - 1 WHERE id = 10;
COMMIT;

✅ Lost Update 방지
⚠️ Serialization 에러 가능 (재시도 필요)
```

### 금융 거래

```sql
-- Serializable
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- 완전한 정확성 필요
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;

✅ 완전한 격리
❌ 성능 저하
⚠️ Serialization 에러 빈번 (재시도 필수)
```

---

## 핵심 요약

### 격리 수준

```
Read Committed (기본값):
- 커밋된 데이터만 읽기
- Non-Repeatable Read 발생 가능
- 대부분의 경우 사용

Repeatable Read:
- 스냅샷 격리
- 트랜잭션 시작 시점 데이터 읽기
- 보고서, 통계에 적합

Serializable:
- 완전한 직렬화
- 모든 이상 현상 방지
- 금융 거래 등에 사용
```

### 문제 발생 여부

```
              | Dirty | Non-Repeatable | Phantom
--------------|-------|----------------|--------
Read Committed| 방지   | 발생            | 발생
Repeatable R. | 방지   | 방지            | 방지*
Serializable  | 방지   | 방지            | 방지

* PostgreSQL의 Repeatable Read는 Phantom Read도 방지
```

### 설정

```sql
-- 트랜잭션 레벨
BEGIN ISOLATION LEVEL REPEATABLE READ;

-- 세션 레벨
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL ...;

-- 데이터베이스 레벨
ALTER DATABASE mydb SET default_transaction_isolation = ...;
```

### 선택 가이드

```
일반 웹: Read Committed
보고서: Repeatable Read
재고: Repeatable Read + FOR UPDATE
금융: Serializable
```
