# Chapter 16. 트랜잭션 기초

## 16.1 트랜잭션이란?

### 정의

```
트랜잭션 (Transaction):
여러 작업을 하나의 논리적 단위로 묶는 것

비유: 은행 계좌 이체
┌─────────────────────────────────┐
│ 송금 과정:                      │
├─────────────────────────────────┤
│ 1. A 계좌에서 10만원 출금       │
│ 2. B 계좌에 10만원 입금         │
└─────────────────────────────────┘

문제 상황:
- 1번만 성공, 2번 실패 → 돈이 사라짐! ❌

트랜잭션으로 해결:
- 둘 다 성공 → COMMIT ✅
- 하나라도 실패 → ROLLBACK (둘 다 취소) ✅
```

### ACID 속성

```
A - Atomicity (원자성)
  트랜잭션은 전부 성공하거나 전부 실패
  "All or Nothing"

C - Consistency (일관성)
  트랜잭션 전후로 데이터 무결성 유지
  "제약조건 항상 만족"

I - Isolation (격리성)
  동시 실행되는 트랜잭션끼리 간섭하지 않음
  "각자 독립적"

D - Durability (지속성)
  커밋된 데이터는 영구 보존
  "정전되어도 데이터 유지"
```

## 16.2 트랜잭션 기본 사용

### BEGIN, COMMIT, ROLLBACK

```sql
-- 트랜잭션 시작
BEGIN;

-- 작업 수행
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 커밋 (확정)
COMMIT;


-- 또는 롤백 (취소)
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 문제 발생!
ROLLBACK;  -- 모든 변경 취소
```

### AUTO COMMIT vs 명시적 트랜잭션

```sql
-- ❌ AUTO COMMIT (기본)
UPDATE users SET name = 'Alice' WHERE id = 1;
-- 즉시 커밋됨! (되돌릴 수 없음)

-- ✅ 명시적 트랜잭션
BEGIN;
UPDATE users SET name = 'Alice' WHERE id = 1;
-- 아직 커밋 안 됨, 다른 세션에서는 안 보임
COMMIT;  -- 이제 커밋!
```

### 실전 예제: 계좌 이체

```sql
-- 테이블 준비
CREATE TABLE accounts (
  id SERIAL PRIMARY KEY,
  user_id INT NOT NULL,
  balance NUMERIC(10, 2) NOT NULL CHECK (balance >= 0)
);

INSERT INTO accounts (user_id, balance) VALUES
(1, 10000),
(2, 5000);


-- ❌ 트랜잭션 없이
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
-- 여기서 에러 발생하면?
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
-- → 1번만 실행됨 (돈 사라짐!)


-- ✅ 트랜잭션 사용
BEGIN;

-- 1번 계좌 출금
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;

-- 2번 계좌 입금
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

-- 확인
SELECT * FROM accounts WHERE id IN (1, 2);
--  id | user_id | balance
-- ----+---------+---------
--   1 |    1    | 9000
--   2 |    2    | 6000

COMMIT;
-- 둘 다 성공! (원자성)


-- 실패 시나리오
BEGIN;

UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
-- 잔액: 8000

UPDATE accounts SET balance = balance + 1000 WHERE id = 999;
-- ERROR: 존재하지 않는 계좌!

ROLLBACK;
-- 1번 계좌도 원래대로! (9000)
```

## 16.3 SAVEPOINT (저장점)

### 정의

```
SAVEPOINT:
트랜잭션 내에서 중간 지점 설정

비유: 게임 저장
┌─────────────────────────────────┐
│ 게임 진행:                      │
├─────────────────────────────────┤
│ 1단계 클리어 → SAVEPOINT A      │
│ 2단계 클리어 → SAVEPOINT B      │
│ 3단계 실패 → ROLLBACK TO B      │
│ 2단계부터 다시 시작!            │
└─────────────────────────────────┘
```

### 기본 사용

```sql
BEGIN;

-- 첫 번째 작업
INSERT INTO users (email, name) VALUES ('alice@ex.com', 'Alice');
SAVEPOINT sp1;

-- 두 번째 작업
INSERT INTO users (email, name) VALUES ('bob@ex.com', 'Bob');
SAVEPOINT sp2;

-- 세 번째 작업
INSERT INTO users (email, name) VALUES ('invalid-email', 'Charlie');
-- 문제 발생!

-- sp2로 롤백 (세 번째 작업만 취소)
ROLLBACK TO SAVEPOINT sp2;

-- Alice, Bob은 유지, Charlie만 취소됨
SELECT * FROM users;
--       email       |  name
-- ------------------+-------
--  alice@ex.com     | Alice
--  bob@ex.com       | Bob

COMMIT;
```

### 실전 예제: 주문 처리

```sql
BEGIN;

-- 주문 생성
INSERT INTO orders (user_id, total_amount)
VALUES (1, 50000)
RETURNING id;
-- id: 100

SAVEPOINT order_created;

-- 주문 상세 추가
INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (100, 10, 2, 20000);

INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (100, 20, 1, 10000);

SAVEPOINT items_added;

-- 재고 차감
UPDATE products SET stock = stock - 2 WHERE id = 10;
UPDATE products SET stock = stock - 1 WHERE id = 20;
-- ERROR: 재고 부족!

-- 재고 차감만 취소
ROLLBACK TO SAVEPOINT items_added;

-- 주문 상태 변경
UPDATE orders SET status = 'pending' WHERE id = 100;

COMMIT;
-- 주문은 생성되지만 재고 차감은 안 됨
```

### SAVEPOINT 해제

```sql
BEGIN;

INSERT INTO users (email, name) VALUES ('alice@ex.com', 'Alice');
SAVEPOINT sp1;

INSERT INTO users (email, name) VALUES ('bob@ex.com', 'Bob');
SAVEPOINT sp2;

-- sp2 해제 (더 이상 sp2로 롤백 불가)
RELEASE SAVEPOINT sp2;

-- sp1으로는 여전히 롤백 가능
ROLLBACK TO SAVEPOINT sp1;

COMMIT;
```

## 16.4 트랜잭션 격리 수준

### Read Uncommitted (가장 낮음)

```sql
-- PostgreSQL은 지원 안 함 (Read Committed로 동작)
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

문제: Dirty Read
- 커밋되지 않은 데이터를 읽을 수 있음
- PostgreSQL은 이 문제를 허용하지 않음
```

### Read Committed (기본값)

```sql
-- 기본 격리 수준
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 세션 1
BEGIN;
UPDATE accounts SET balance = 5000 WHERE id = 1;
-- 아직 커밋 안 됨

-- 세션 2
SELECT balance FROM accounts WHERE id = 1;
-- 10000 (이전 값, 커밋된 데이터만 읽음)

-- 세션 1
COMMIT;

-- 세션 2
SELECT balance FROM accounts WHERE id = 1;
-- 5000 (커밋된 새 값)


특징:
✅ Dirty Read 방지
❌ Non-Repeatable Read 발생 가능
❌ Phantom Read 발생 가능
```

### Repeatable Read

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
-- 10000

-- 세션 2
BEGIN;
UPDATE accounts SET balance = 5000 WHERE id = 1;
COMMIT;

-- 세션 1 (같은 트랜잭션)
SELECT balance FROM accounts WHERE id = 1;
-- 10000 (여전히 이전 값! 스냅샷 격리)

COMMIT;

-- 이제 다시 읽으면
SELECT balance FROM accounts WHERE id = 1;
-- 5000


특징:
✅ Dirty Read 방지
✅ Non-Repeatable Read 방지
❌ Phantom Read 발생 가능 (PostgreSQL은 사실상 방지)
```

### Serializable (가장 높음)

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 완전한 직렬화
-- 동시 트랜잭션이 순차적으로 실행되는 것처럼 동작

특징:
✅ Dirty Read 방지
✅ Non-Repeatable Read 방지
✅ Phantom Read 방지
❌ 성능 저하
❌ Serialization 에러 발생 가능
```

### 격리 수준 비교

```
격리 수준         | Dirty Read | Non-Repeatable | Phantom Read | 성능
-----------------|------------|----------------|--------------|------
Read Uncommitted | 가능        | 가능            | 가능          | 최상
Read Committed   | 방지        | 가능            | 가능          | 좋음 ⭐ (기본)
Repeatable Read  | 방지        | 방지            | 가능          | 보통
Serializable     | 방지        | 방지            | 방지          | 나쁨
```

### 실전 예제: 좌석 예약

```sql
-- Read Committed (문제 발생)
-- 세션 1
BEGIN;
SELECT seat_number FROM seats WHERE is_booked = false LIMIT 1;
-- seat_number: A1

-- 세션 2
BEGIN;
SELECT seat_number FROM seats WHERE is_booked = false LIMIT 1;
-- seat_number: A1 (같은 좌석!)

-- 세션 1
UPDATE seats SET is_booked = true WHERE seat_number = 'A1';
COMMIT;

-- 세션 2
UPDATE seats SET is_booked = true WHERE seat_number = 'A1';
COMMIT;
-- 중복 예약!


-- Repeatable Read (해결)
-- 세션 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT seat_number FROM seats WHERE is_booked = false LIMIT 1 FOR UPDATE;
-- seat_number: A1, LOCK 획득

-- 세션 2
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT seat_number FROM seats WHERE is_booked = false LIMIT 1 FOR UPDATE;
-- 대기... (세션 1이 커밋할 때까지)

-- 세션 1
UPDATE seats SET is_booked = true WHERE seat_number = 'A1';
COMMIT;

-- 세션 2
-- 이제 A1 제외하고 다음 좌석 반환
-- seat_number: A2
```

## 16.5 잠금 (Locking)

### 행 단위 잠금

```sql
-- FOR UPDATE (배타적 잠금)
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- 다른 트랜잭션은 이 행을 UPDATE/DELETE 불가 (대기)

UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
COMMIT;


-- FOR SHARE (공유 잠금)
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR SHARE;
-- 다른 트랜잭션은 읽기 가능, 쓰기 불가

COMMIT;
```

### FOR UPDATE 옵션

```sql
-- NOWAIT (대기 안 함)
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- 잠금 획득 실패 시 즉시 에러
-- ERROR: could not obtain lock on row

ROLLBACK;


-- SKIP LOCKED (잠긴 행 건너뛰기)
BEGIN;
SELECT * FROM tasks WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 잠긴 행은 건너뛰고 다음 행 반환
-- 작업 큐 구현에 유용!

COMMIT;
```

### 실전 예제: 작업 큐

```sql
-- 작업 테이블
CREATE TABLE tasks (
  id SERIAL PRIMARY KEY,
  status VARCHAR(20) DEFAULT 'pending',
  worker_id INT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Worker 1
BEGIN;
UPDATE tasks
SET status = 'processing', worker_id = 1
WHERE id = (
  SELECT id FROM tasks
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
-- task id: 10

-- 작업 처리...

UPDATE tasks SET status = 'completed' WHERE id = 10;
COMMIT;


-- Worker 2 (동시 실행)
BEGIN;
UPDATE tasks
SET status = 'processing', worker_id = 2
WHERE id = (
  SELECT id FROM tasks
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
-- task id: 11 (10은 건너뜀!)

UPDATE tasks SET status = 'completed' WHERE id = 11;
COMMIT;
```

## 16.6 데드락 (Deadlock)

### 데드락이란?

```
데드락 (Deadlock):
두 개 이상의 트랜잭션이 서로 잠금을 기다리며 무한 대기

비유: 교차로 막힘
┌─────────────────────────────────┐
│        ↑                        │
│        │                        │
│   ← 🚗 🚗 →                     │
│        │                        │
│        ↓                        │
└─────────────────────────────────┘
모두가 서로를 기다림 → 무한 대기!
```

### 데드락 발생 예제

```sql
-- 세션 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- LOCK on id = 1

-- 세션 2
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 2;
-- LOCK on id = 2

-- 세션 1
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- 대기... (세션 2가 id=2 잠금 중)

-- 세션 2
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
-- 대기... (세션 1이 id=1 잠금 중)

-- PostgreSQL이 자동 감지 (1초 후)
-- ERROR: deadlock detected
-- DETAIL: Process 1234 waits for ShareLock on transaction 5678
```

### 데드락 방지 전략

```sql
-- 1. 잠금 순서 일관성
-- ❌ 나쁜 예
-- 트랜잭션 1: LOCK(A) → LOCK(B)
-- 트랜잭션 2: LOCK(B) → LOCK(A)

-- ✅ 좋은 예
-- 트랜잭션 1: LOCK(A) → LOCK(B)
-- 트랜잭션 2: LOCK(A) → LOCK(B)

BEGIN;
UPDATE accounts SET balance = balance - 100
WHERE id IN (1, 2)
ORDER BY id;  -- 항상 ID 순서대로!
COMMIT;


-- 2. 잠금 시간 최소화
BEGIN;
-- 빠른 작업만
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- 느린 작업 (외부 API 호출 등)은 트랜잭션 밖에서


-- 3. NOWAIT 사용
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- 잠금 실패 시 즉시 에러, 재시도 로직 구현
COMMIT;
```

### 데드락 확인

```sql
-- 현재 잠금 상황
SELECT
  l.pid,
  l.mode,
  l.granted,
  a.usename,
  a.query,
  a.state
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE NOT l.granted;

-- 데드락 발생 시 로그 확인
-- /var/log/postgresql/postgresql-15-main.log
-- ERROR: deadlock detected
```

## 16.7 실전 시나리오

### 시나리오 1: 전자상거래 주문

```sql
-- 주문 처리 (트랜잭션 필수!)
BEGIN;

-- 1. 재고 확인 및 차감
UPDATE products
SET stock = stock - 1
WHERE id = 10
  AND stock >= 1
RETURNING stock;

-- 재고 부족 시
IF NOT FOUND THEN
  ROLLBACK;
  RAISE EXCEPTION '재고 부족';
END IF;

-- 2. 주문 생성
INSERT INTO orders (user_id, total_amount, status)
VALUES (1, 50000, 'pending')
RETURNING id INTO order_id;

-- 3. 주문 상세 생성
INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (order_id, 10, 1, 50000);

-- 4. 결제 처리 (외부 API)
-- 성공 시
UPDATE orders SET status = 'paid' WHERE id = order_id;

COMMIT;
-- 모두 성공 또는 모두 실패!
```

### 시나리오 2: 포인트 적립/차감

```sql
-- 포인트 차감
BEGIN;

-- 1. 현재 포인트 확인 (잠금)
SELECT point_balance
FROM users
WHERE id = 1
FOR UPDATE;
-- point_balance: 5000

-- 2. 차감
UPDATE users
SET point_balance = point_balance - 1000
WHERE id = 1
  AND point_balance >= 1000;

-- 3. 포인트 히스토리 기록
INSERT INTO point_history (user_id, amount, type, description)
VALUES (1, -1000, 'use', '상품 구매');

COMMIT;


-- 동시에 여러 요청 와도 안전!
-- FOR UPDATE로 순차 처리
```

### 시나리오 3: 좌석 예약

```sql
-- 좌석 예약 (동시성 제어)
BEGIN ISOLATION LEVEL REPEATABLE READ;

-- 1. 빈 좌석 찾기 (잠금)
SELECT id, seat_number
FROM seats
WHERE screening_id = 100
  AND is_booked = false
ORDER BY seat_number
LIMIT 1
FOR UPDATE SKIP LOCKED;  -- 잠긴 좌석 건너뛰기
-- id: 50, seat_number: 'A1'

-- 2. 예약
UPDATE seats
SET is_booked = true, user_id = 1, booked_at = NOW()
WHERE id = 50;

-- 3. 예약 기록
INSERT INTO reservations (user_id, screening_id, seat_id)
VALUES (1, 100, 50);

COMMIT;
-- 중복 예약 방지!
```

### 시나리오 4: 게시글 조회수 증가

```sql
-- ❌ 나쁜 예 (트랜잭션 불필요)
BEGIN;
UPDATE posts SET view_count = view_count + 1 WHERE id = 100;
COMMIT;
-- 조회수는 정확하지 않아도 됨, 트랜잭션 오버헤드만

-- ✅ 좋은 예
UPDATE posts SET view_count = view_count + 1 WHERE id = 100;
-- AUTO COMMIT, 빠름!

-- 또는 배치 처리
-- Redis 등에 카운트 저장 후 주기적으로 DB 업데이트
```

## 16.8 트랜잭션 모니터링

### 활성 트랜잭션 확인

```sql
-- 현재 실행 중인 트랜잭션
SELECT
  pid,
  usename,
  state,
  query,
  xact_start,
  NOW() - xact_start AS duration
FROM pg_stat_activity
WHERE state = 'active'
  AND xact_start IS NOT NULL
ORDER BY xact_start;

--  pid  | usename | state  | query              | duration
-- ------+---------+--------+--------------------+-----------
--  1234 | user1   | active | UPDATE accounts... | 00:05:23
--  5678 | user2   | active | INSERT INTO...     | 00:00:02
--                            ↑ 5분 넘은 트랜잭션 → 문제 의심
```

### 오래 실행 중인 트랜잭션 찾기

```sql
-- 5분 이상 실행 중인 트랜잭션
SELECT
  pid,
  usename,
  query,
  NOW() - xact_start AS duration
FROM pg_stat_activity
WHERE xact_start < NOW() - INTERVAL '5 minutes'
  AND state != 'idle'
ORDER BY xact_start;

-- 강제 종료
SELECT pg_terminate_backend(1234);
```

### 잠금 대기 확인

```sql
-- 잠금 대기 중인 쿼리
SELECT
  blocked.pid AS blocked_pid,
  blocked.query AS blocked_query,
  blocking.pid AS blocking_pid,
  blocking.query AS blocking_query
FROM pg_stat_activity AS blocked
JOIN pg_locks AS blocked_locks ON blocked.pid = blocked_locks.pid
JOIN pg_locks AS blocking_locks ON blocked_locks.locktype = blocking_locks.locktype
  AND blocked_locks.relation = blocking_locks.relation
JOIN pg_stat_activity AS blocking ON blocking_locks.pid = blocking.pid
WHERE NOT blocked_locks.granted
  AND blocking_locks.granted;

--  blocked_pid | blocked_query       | blocking_pid | blocking_query
-- -------------+---------------------+--------------+----------------
--  5678        | UPDATE accounts...  | 1234         | UPDATE accounts...
```

## 16.9 트랜잭션 패턴

### 패턴 1: Try-Catch 트랜잭션

```sql
-- PL/pgSQL
DO $$
BEGIN
  BEGIN
    -- 트랜잭션 시작
    INSERT INTO users (email, name) VALUES ('alice@ex.com', 'Alice');
    INSERT INTO posts (user_id, title) VALUES (1, 'Hello');

    -- 성공 시 자동 커밋
  EXCEPTION
    WHEN OTHERS THEN
      -- 에러 발생 시 롤백
      RAISE NOTICE 'Error: %', SQLERRM;
      -- 자동 롤백
  END;
END $$;
```

### 패턴 2: 낙관적 잠금 (Optimistic Locking)

```sql
-- version 컬럼 추가
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name VARCHAR(255),
  price NUMERIC(10, 2),
  version INT DEFAULT 0
);

-- 업데이트 시 version 확인
UPDATE products
SET
  price = 60000,
  version = version + 1
WHERE id = 10
  AND version = 5;  -- 읽었을 때의 version

-- 0 rows affected → 다른 트랜잭션이 먼저 수정함!
-- 재시도 필요
```

### 패턴 3: 비관적 잠금 (Pessimistic Locking)

```sql
-- 읽을 때부터 잠금
BEGIN;

SELECT * FROM products WHERE id = 10 FOR UPDATE;
-- 즉시 잠금

UPDATE products SET price = 60000 WHERE id = 10;

COMMIT;
```

## 16.10 트랜잭션 최적화

### 1. 트랜잭션 크기 최소화

```sql
-- ❌ 나쁜 예: 트랜잭션이 너무 큼
BEGIN;
-- 수만 건 처리
FOR i IN 1..100000 LOOP
  INSERT INTO logs (message) VALUES ('Log ' || i);
END LOOP;
COMMIT;
-- 잠금 시간 길어짐, 롤백 시 오래 걸림


-- ✅ 좋은 예: 배치 나누기
FOR batch IN 0..99 LOOP
  BEGIN;
  -- 1000건씩 처리
  INSERT INTO logs (message)
  SELECT 'Log ' || i
  FROM generate_series(batch * 1000 + 1, (batch + 1) * 1000) AS i;
  COMMIT;
END LOOP;
```

### 2. 읽기 전용 트랜잭션

```sql
-- 읽기 전용 트랜잭션 (최적화)
BEGIN TRANSACTION READ ONLY;
SELECT * FROM users WHERE country = 'Korea';
SELECT * FROM posts WHERE user_id = 1;
COMMIT;

-- 장점:
-- - 잠금 없음
-- - 성능 향상
-- - 데이터 무결성 유지
```

### 3. 트랜잭션 밖으로 이동

```sql
-- ❌ 나쁜 예
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 100;
-- 외부 API 호출 (느림!)
CALL send_email_notification(100);
COMMIT;


-- ✅ 좋은 예
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 100;
COMMIT;

-- 트랜잭션 밖에서 알림 발송
CALL send_email_notification(100);
```

## 핵심 요약

### ACID

```
Atomicity    - 전부 성공 또는 전부 실패
Consistency  - 데이터 무결성 유지
Isolation    - 트랜잭션 간 독립성
Durability   - 커밋된 데이터 영구 보존
```

### 기본 명령

```sql
BEGIN;              -- 트랜잭션 시작
COMMIT;             -- 확정
ROLLBACK;           -- 취소

SAVEPOINT sp1;      -- 저장점
ROLLBACK TO sp1;    -- 저장점으로 롤백
RELEASE sp1;        -- 저장점 해제
```

### 격리 수준

```sql
READ COMMITTED      -- 기본값, 커밋된 데이터만 읽기
REPEATABLE READ     -- 스냅샷 격리
SERIALIZABLE        -- 완전한 직렬화
```

### 잠금

```sql
FOR UPDATE          -- 배타적 잠금
FOR SHARE           -- 공유 잠금
NOWAIT              -- 대기 안 함
SKIP LOCKED         -- 잠긴 행 건너뛰기
```

### 권장 사항

```
✅ 해야 할 것:
- 금융, 재고, 주문 등 → 트랜잭션 필수
- 트랜잭션 크기 최소화
- 잠금 시간 최소화
- 데드락 방지 (순서 일관성)

❌ 하지 말아야 할 것:
- 조회수, 로그 → 트랜잭션 불필요
- 트랜잭션 안에서 느린 작업 (외부 API)
- 너무 긴 트랜잭션
```
